## 2. Target workflow and responsibility split

Developer: make a focused change, add a forward migration when schema changes, run focused local checks, commit and push. CircleCI: build and test the exact commit, test fresh install and upgrade, publish images, capture full SHA and per-image digest in a release manifest. It must not SSH to the VPS as a side effect of a push until an explicitly designed deploy gate exists. Developer invokes deployment for a selected approved manifest. VPS-side Maevelle-only scripts perform preflight, backup when required, one-time migration, selective service update, verification and release-record write. Manual authorization governs staging reset and destructive restore; a normal deploy is an operator-triggered action with clear logs.

| Conceptual command | Existing equivalent | Recommended owner and behavior |
| --- | --- | --- |
| `deploy` | No VPS command in repo | Local thin invocation passes manifest/release ID to VPS Maevelle deploy script; VPS script verifies digest, compatibility, target identity, then updates selected Quadlets |
| `status` | `db:migrate:status`, Compose `db:status`, smoke script | VPS read-only status combines current/previous release, exact digests, systemd user units, health, migration ledger, and recent errors |
| `migrate` | Database CLI, staging Compose one-shot service | VPS one-time job from target API image, serialized with a deployment lock; preflight/status before applying |
| `reset` | Local `docker compose down --volumes` only | VPS explicit staging-only recovery workflow, never CI push-triggered; independent of normal deploy |
| `seed` | `db:seed`, `seed:staging`, Owner bootstrap | VPS one-time, explicit after fresh install/reset; improve guard and deterministic synthetic dataset, keep credentials external |
| `backup` | Local Docker script | VPS scoped `pg_dump` plus media snapshot and manifest; private storage and a separately verified restore drill |
| `restore` | Local `restore:drill` only | VPS manual, destructive staging operation using selected backup, target confirmation and downtime; test first on isolated database |
| `rollback` | No command | VPS selects prior compatible image digests, no automatic database down migration; otherwise forward-fix or restore coordinated backup |

Avoid duplicating Kysely or seed logic in shell: wrappers call the existing compiled CLIs. Use one serialization lock for deploy/migrate/reset/restore. A release manifest contains source full SHA, image names and immutable digests, build result, schema compatibility notes, and creation time. The VPS records previous/current manifests and step logs outside the application containers. Use the digest for pulling; the `staging-<short SHA>` tag is a human aid, not an immutable guarantee.

Selective deployment is safe only after checking shared contracts and schema compatibility. UI-only changes may update Admin or Storefront alone. API/Worker message, schema, auth, or public contract changes may require a coordinated group update. PostgreSQL and Caddy should not be restarted just because application images changed. Stop on preflight or migration failure before changing application units; retain the failed manifest, job output, and prior running release. After partial service failure, restore compatible prior images only if they work with the migrated schema; otherwise use a forward repair.

## 3. Database lifecycle

1. **Normal development:** each schema change adds a new migration to the explicit registry. Do not edit applied files. Include data transformation when needed. Review Kysely's migration ordering, transactional behavior, and lock behavior against the actual implementation before automating the one-time job. CI constructs a fresh PostgreSQL 18 database from all checked-in migrations and upgrades a database built from the previous deployable commit; verify expected data and application startup. Keep a small prior-release fixture or build prior-release schema in CI.
2. **Before deployment:** compare VPS ledger and relevant schema objects read-only with the release baseline. Resolve any historic drift, especially the `0300`/`3200` issue, using a reviewed forward reconciliation migration or an explicitly coordinated reset. Back up and verify restore readiness before breaking migrations. Declare the last compatible app release and whether API/Worker can overlap during upgrade. Use expand/migrate/contract when overlap is required; otherwise schedule short downtime and deploy as a compatible unit.
3. **Reset:** require manual authorization, exact staging host/user/database identifiers, an explicit typed confirmation, a checked backup and media decision, a non-production environment sentinel, and a scoped Podman volume/database target. Stop Maevelle writers only; never use a broad host prune or unscoped Compose volume removal. Recreate the database, run migrations once, bootstrap organization/Owner, run deterministic synthetic seed, then verify. Record backup ID, release, and result.
4. **Rebaseline:** exceptional development operation. Inventory all environments and applied ledgers, choose coordinated resets or forward reconciliation, update migration registry/test fixtures, verify clean build and upgrade behavior, then record the new base commit. Never let a changed migration file quietly masquerade as an unapplied upgrade.

Staging data survives ordinary deployment. Staging seed is an explicit operation, not an API/Worker startup dependency. `compose.staging.yaml` currently chains `migrate -> bootstrap-owner -> seed-staging -> API/Worker`, which conflicts with this desired ordinary-deploy behavior and must be changed only in a later implementation phase. Do not treat `ALLOW_STAGING_SEED=1` alone as a safe reset or seed authorization.

## 4. Network, media, origins and secrets

Keep the current host topology: public HTTPS hostname -> shared Nginx vhost -> Maevelle private Caddy listener -> isolated API/Admin/Storefront; Worker and PostgreSQL remain internal. Nginx and all other sites are shared host assets and excluded from routine Maevelle deploy. Before opening access, verify actual listener binding, firewall and rootless Podman network; `compose.staging.yaml` uses `${CADDY_PORT}:80` without a loopback bind and must not be copied unchanged to a publicly reachable host. Keep DB and app ports unexposed. Any shared Nginx hostname change is a separate, reviewed host task.

Use one canonical HTTPS public origin where practical. In the verified private staging setup, `BETTER_AUTH_URL=http://127.0.0.1:18080` is the correct origin: Fastify Better Auth uses `basePath: '/auth'`, while Caddy strips the external `/api` prefix before forwarding `/api/auth/*`. `GET /api/auth/get-session` returned 200, an empty sign-in POST returned 400, and the Owner subsequently signed in. For a future hostname, use its HTTPS **origin** as `BETTER_AUTH_URL` without `/api`; configure `AUTH_TRUSTED_ORIGINS`, `STOREFRONT_BASE_URL`, Storefront organization code, OAuth/webhook callbacks, secure cookie behavior and proxy forwarding consistently. Admin and Storefront browser clients call `/api/auth/*` directly; check `/api/*` stripping, Admin `/admin` basePath, Storefront links and redirects on desktop and mobile. The config's local fallback URL contains `/api`, but the verified staging env value overrides it. Next rewrites hard-code localhost for development and should be assessed separately for build-time versus runtime use. Keep build output free of host-specific secrets; public settings baked into a Next build require a rebuild when changed.

The staging Compose file declares only a PostgreSQL volume. API Dockerfile creates `/app/var/media` in the image, and `.env.staging.example` points local media there; no persistent staging media mount is declared. Verify actual Podman media mount and backup scope before an update. Use service-specific secret files or protected environment on VPS, strict permissions, secret redaction, and no credentials in Git, manifests or CI logs. Avoid real provider effects from synthetic fixtures.

## 5. Recovery and verification

Before rollout, retain a database backup and media snapshot appropriate to the change, with release ID and timestamp. Test restore into an isolated target; do not equate a successful `pg_dump` with recoverability. Normal image rollback reads the previous manifest and compatibility note, pulls pinned digests, updates only affected Maevelle units, and verifies health. It does not undo SQL. Incompatible migrations require forward repair or downtime plus coordinated database/media restore and compatible image rollout. Preserve logs and backup IDs through failed attempts.

Deployment verification: migration status, all required user units active, API `/health/live` and `/health/ready`, worker heartbeat/queue health, public route smoke (`scripts/staging-smoke.mjs` can be reused), an authenticated Admin sign-in/session check, a Storefront browse/cart flow, and targeted behavior for changed areas. Log step timing and errors without secrets. CI and repository checks establish candidate quality; only VPS status and browser checks establish deployment success.
