## B. Risks and gaps

1. **No proven recovery point for staging.** No repository evidence shows an automated, encrypted, off-host database and media backup, a retention policy, or a complete isolated restore. Manually created staging records may be the only copy.
2. **Database/media time skew.** [PostgreSQL 18 `pg_dump`](https://www.postgresql.org/docs/18/app-pgdump.html) gives a consistent database snapshot during concurrent writes. It cannot make the filesystem media snapshot atomic with that database snapshot. Uploads, deletes, transformations and worker jobs can otherwise produce missing objects after recovery.
3. **Incomplete local drill.** The Docker helper's schema count cannot prove data, authentication, privileges, media checksums or application start. An interrupted local drill can leave temporary files or a disposable database; it never touches staging but must not be promoted unchanged.
4. **Bootstrap ambiguity.** A restored Owner's password hash and multifactor state are database data. Re-running bootstrap against an existing user does not reset a lost password. A fresh rebuild needs a separately held password and an authenticated sign-in check. Auth cryptographic settings (`BETTER_AUTH_SECRET`, `AUTH_ENCRYPTION_KEY`) live outside the database and must be recoverable without logging them.
5. **Seed guard and effects.** `ALLOW_STAGING_SEED=1` is insufficient authorization. The current sample uses production business transitions, which can create outbox work; provider delivery must be disabled or routed to safe test sinks during a rebuild. Random keys and whole-domain count guards need repeatability tests before claiming deterministic fixtures.
6. **Rollback boundary.** Phase 03 can restore compatible application image references, but cannot undo SQL, recover deleted rows, or replace media. A reset or destructive restore is a downtime operation with a new recovery point, not an image rollback.
7. **Configuration and global objects.** [`pg_dump` covers one database, not cluster-wide roles or tablespaces](https://www.postgresql.org/docs/18/backup-dump.html). The protected Maevelle environment, Quadlets, Caddy configuration, role/extension requirements, and release manifest need a separate, access-controlled recovery inventory. Do not dump the whole PostgreSQL cluster or other applications to compensate.

## C. Recommended architecture

### 1. Recovery set and invariants

Treat a recovery point as a **single immutable set**: PostgreSQL 18 custom-format dump of exactly `maevelle_staging`, matching `maevelle-staging-media` content, a machine-readable manifest, and a separately protected configuration/secret recovery inventory. The manifest records a unique backup ID, UTC start/end, target host fingerprint (nonsecret), source database and volume identities, PostgreSQL/client versions, release full SHA and four image digests, migration-ledger names/hash, media file count/total bytes, per-artifact SHA-256, encryption format/key ID, quiescence interval, and verification state. Do not place credentials, personal data, raw environment values or media paths containing sensitive names in public metadata.

Use the existing Maevelle rootless user and **the same `maevelle-staging-migration.lock`** for backup quiescence, migration, deployment, restore and reset. That lock serializes Maevelle tooling only; it does not stop app writes by itself. Refuse missing/ambiguous names, symlinks, wrong ownership, non-rootless execution, unexpected mounts, changed release/schema during capture, and any target outside the allowlist. A separate read-only `plan` must show identity, affected Maevelle services, backup ID, data-loss window, and the exact operations before any destructive action.

### 2. Backup, integrity, retention and consistency

Use a PostgreSQL 18 client of the same major version, `pg_dump -Fc`, with error propagation and a private temporary output path; never copy a running PostgreSQL data directory as a logical backup. Inspect the archive with `pg_restore --list`, calculate SHA-256 after the file is complete, and publish it atomically only after both artifacts and manifest are complete. An archive list and hash detect transfer damage; **only an isolated restore can establish usability**. Capture database identity and ledger before and after; abort and discard the unpublished candidate if either changes.

Two backup classes are appropriate:

- **Routine database-only checkpoint:** may run online for low-cost row recovery, labeled explicitly `database-only` and never eligible for coordinated database/media restore. It cannot meet the Phase 04 recovery gate by itself.
- **Coordinated recovery set:** announce a short Maevelle-only maintenance window, block write ingress and provider callbacks, stop or drain API and Worker plus any other Maevelle media writer, wait for in-flight transactions and media writes to finish, then capture DB and media while writers remain quiesced. Leave PostgreSQL, Caddy, host Nginx and unrelated services untouched. Verify dump completion and a media inventory/checksum before reopening Maevelle writes. If quiescence cannot be proven, fail the coordinated set; do not silently relabel it recoverable. Scheduled ordinary backups may use this window at a time approved by the operator.

Copy encrypted artifacts to a separate storage failure domain with a Maevelle-scoped write credential, protected encryption key and retrieval test. A local copy can speed restore but is not a host-loss backup. Proposed starting policy: one coordinated set per day, retain 14 daily and 8 weekly sets; pin every pre-migration/pre-reset set until the linked release is accepted and at least one newer set passes an isolated drill. Set a minimum of two independently verified sets before pruning; deletion is based on completed set IDs, never a wildcard over the host. Alert on failed capture, upload, verification, low space and missed schedule. Confirm storage cost, recovery objectives and retention with the operator before enabling scheduling. Logical dumps provide a snapshot, not point-in-time recovery; if the accepted recovery-point objective becomes shorter than the schedule, design PostgreSQL physical backup plus WAL archiving as a separate, tested change ([PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)).

### 3. Isolated restoration verification

Fetch a recovery set **from the off-host copy**, verify artifact hashes and decrypt into a private temporary area. Restore into a fresh PostgreSQL 18 container and disposable volume/database on a dedicated private network with no public listener, no route to staging or other VPS apps, and no real provider credentials. Do not use `maevelle_staging` as the drill target. Validate the required role/extension setup from a reviewed Maevelle-only inventory; use `pg_restore --exit-on-error` and explicit ownership/privilege mapping suited to the isolated role. For small current data, a single transaction can be considered after testing lock/resource needs ([`pg_restore` options](https://www.postgresql.org/docs/18/app-pgrestore.html)).

Restore media into a separate disposable directory/volume. Verify every database-referenced local object that is expected to exist, its byte count/checksum where recorded, and public/private access behavior through a test API using only inert provider settings. Check ledger and release compatibility, representative row counts and domain invariants (organization/Owner, products, orders, inventory balances, finance references, outbox state), and an authenticated Owner test account in an **isolated synthetic drill**. A staging-data drill must avoid exposing the real Owner session/credentials; use a protected operator check or a synthetic user created solely in the isolated copy. Retain a sanitized drill report with backup ID, release, timings, checks performed, and failures. Destroy only the named disposable drill resources after evidence is saved. A corruption or missing-media test must fail closed.

Run an isolated restore after initial setup, after backup-format/tooling changes, before a risky migration/reset, and at least monthly thereafter. Rotate which retained set is tested, including an off-host fetched set. Maintain measured recovery time and age of latest verified set; do not mark a set `restorable` on checksum/list success alone.

### 4. Preservation, restore and reset workflows

**Ordinary deploy:** retain staging PostgreSQL and media volumes. Phase 03 deploy remains independent of seed/reset. Before a schema-changing deployment, require a recent coordinated, restorable recovery set and a declared last compatible image release plus forward-repair path. Migration remains the separate one-time Phase 02 job.

**Recovery of staging data:** prefer forward repair for a narrow defect. For destructive restoration, obtain explicit operator approval of backup ID, target, expected data-loss interval, paired media policy and compatible app images. Quiesce Maevelle writers, take a fresh pre-restore rescue set even if data appears damaged, and preserve current release/diagnostics. Restore to **new** Maevelle-only database/media targets first, verify there, then switch Maevelle configuration/volume references in a controlled cutover with the old targets retained for rollback. Do not overwrite a live volume in place; do not start API/Worker against a partially restored pair. Record cutover and perform health/auth/media/business smoke checks. Return service only after all checks pass; otherwise roll back the cutover to the retained original pair if still valid, or keep maintenance mode and investigate. Database rollback to an older point loses intervening writes, queued jobs, sessions and provider reconciliation state; external side effects are not reversed.

**Intentional staging reset:** an operator-only command, never called by CI, push, deploy, migration, API/Worker startup or Compose dependencies. Require a read-only plan, nonproduction sentinel, exact host/user/container/database/volume identity, same lock, a recently **verified coordinated** off-host recovery set, a fresh pre-reset rescue set, a selected target release manifest, a media disposition, and typed confirmation containing both `maevelle_staging` and the unique plan/backup ID. The confirmation expires if plan inputs change. Quiesce Maevelle writers and preserve old database/media targets; create new empty Maevelle-only targets rather than deleting existing volumes. Replay all registered migrations once from the selected digest, check ledger/schema and baseline hash, bootstrap one organization and active Owner from protected external input, run versioned synthetic seeds once, verify repeated seed execution causes no unintended new business state, then start the compatible app set and perform focused checks. Only a later, separately approved retention operation may remove old targets after restore proof and the agreed hold period. A failed reset keeps old targets and diagnostics; never auto-retry by deleting anything.

### 5. Seed and Owner contract

Split **canonical reference data** from **synthetic operational fixtures**. Make each fixture stable by an explicit version, organization-scoped natural keys and stable idempotency keys; use domain commands so inventory, costing, payments and audit/outbox invariants remain authoritative. Never update or delete manually created staging records merely to make a fixture match; report collisions and require operator resolution. Test rerun after full completion and interruption at every meaningful stage. A fresh rebuild must produce the same fixture identities and business totals from the same version, except generated opaque identifiers/timestamps where deliberately nonsemantic. If a fixture requires media, package synthetic media with checksums or omit that fixture with an explicit acceptance change.

Keep Owner sign-in independent from seed. On a **restore**, retain the Owner row, password hash, MFA state and secrets from the paired recovery set; recover the matching external cryptographic settings from protected storage. On a **fresh reset**, use a one-time external password delivery and require an interactive sign-in/MFA enrollment or a reviewed recovery flow. Never store password, TOTP secret, recovery codes or encryption keys in the seed, manifest or logs. If the Owner cannot authenticate, do not declare reset complete; use a separately authorized Owner recovery procedure that verifies organization identity, invalidates sessions as appropriate, and records an audit event. The existing bootstrap CLI is not such a recovery procedure.

### 6. Isolation and failure behavior

All tooling runs as rootless `maevelle`, with Maevelle-only volume/container/unit allowlists, fixed private network and protected `0700` directories/`0600` artifacts. Grant a backup role only the database read/lock privileges needed for a complete dump; role creation and extension restore are separate narrowly scoped tasks. Do not grant the backup process blanket host root, Docker socket, Nginx control, or access to unrelated containers/volumes. Use short-lived off-host credentials, encryption at rest and in transit, and a separately recoverable key. Redact command output and error reports; personal data in dumps remains sensitive even in staging.

Failure matrix: dump/upload/media capture failure leaves current data untouched and a failed candidate unpublishable; restore verification failure blocks pruning/reset/migration gate; mid-reset failure leaves old pair available and Maevelle in maintenance; cutover health failure returns to old pair only if no writes occurred on the new pair, otherwise requires operator reconciliation. Image rollback uses only a release compatible with the **current** schema. Neither a PostgreSQL logical dump nor an image rollback provides point-in-time recovery, recovery of later provider side effects, or proof that a compromised host's secrets are safe.

## Phase 04.1 — implemented contracts and evidence still needed

The portable format is `scripts/recovery/contract.py` version 1. It requires a `mvl-stg-<UTC>-<random>` recovery-set ID, exact staging user/UID/network/database/volume identity and a nonsecret 32-hex host fingerprint, PostgreSQL 18 server/client versions, a full application release SHA, exactly four digest-pinned GHCR image references, sorted baseline-compatible migration names and SHA-256 of their newline-joined names, an encrypted database artifact and (for coordinated sets) an encrypted media artifact with nonzero byte sizes and SHA-256 digests. It also binds capture time, recovery-point time, quiescence evidence, off-host reference, integrity readback, and a separate isolated-restore report ID/hash to the set ID and migration hash. Artifact names and off-host object keys are restricted to safe relative identifiers. Passwords, secret values and host filesystem paths are not contract fields. Version 1 currently names `age` as the encryption method; its actual key and off-host provider remain an operator decision for Phase 04.2.

The state sequence is `candidate → captured → transferred → integrity-verified → restore-verified`, with `failed` terminal from any unfinished state. Skips and reversals are rejected. `captured` requires complete artifacts and matching before/after ledger hashes; `transferred` requires an off-host reference; `integrity-verified` requires matching hashes and off-host readback; `restore-verified` requires an isolated restore evidence record bound to this set and migration ledger. `coordinated_eligible()` returns true only for a coordinated, restore-verified set. Database-only checkpoints carry no media artifact or media recovery point and can never satisfy that predicate. The validator enforces evidence *shape*; a future trusted capture/drill implementation must produce and authenticate the evidence. A hand-edited JSON file does not prove recoverability.

Future writers must use the existing `/run/user/1001/maevelle-staging-migration.lock` (or the identical `$XDG_RUNTIME_DIR` path) for backup, restore and reset, sharing it with Phase 02 migration and Phase 03 deployment. They must refuse a different runtime directory, root/non-`maevelle` identity, missing staging sentinel, any database other than `maevelle_staging`, or volumes other than `maevelle-staging-postgres` and `maevelle-staging-media`. Treat backup IDs as immutable. Check each parent against symlinks and traversal, ensure protected files are owned by `maevelle` with no group/other access, and publish only complete artifacts plus manifest by atomic rename after file/directory sync and checksum verification. Never publish a partial set under its final ID. Ambiguous names, duplicate mounts, stale release/ledger or any changed plan input cause refusal. Phase 04.1 defines this contract; it does not yet create lock-taking backup/reset tooling.

The deployed application release remains `87fec723c9fcfa30424f82c7520c984bded477f3`; local HEAD is not used as a release claim.

The repository writer audit found API uploads/deletes and Worker media jobs plus provider attachment ingestion. Browser uploads and provider callbacks enter through the API. Coordinated capture stops both scoped units, verifies clean inactive containers, zero remaining PostgreSQL client sessions and exact surviving Maevelle network members, captures database and media under that boundary, rechecks the ledger and media counts, then starts API followed by Worker and checks API readiness. Caddy, PostgreSQL, host Nginx and other sites remain untouched. A missing Worker volume mount, altered media backend, ambiguous network membership, unclean stop, active session or changed ledger refuses publication. Stopping API causes a Maevelle-only outage, and provider retries/side effects are not captured. The exact deployed Quadlet stop timeout and Worker mount remain **live verification blockers** for coordinated execution.

The storage boundary uses `age` recipients and a provider-neutral interface with an opt-in approved remote filesystem mount. No provider credentials are in code or portable metadata. A remote mount must be shown to have reliable rename/hard-link/fsync/readback semantics and be in a separate failure domain. Until the sentinel, key custody, off-host mount and approvals exist, live execution is blocked. Local tests exercise transfer against disposable directories only. A local checksum or off-host readback advances to `integrity-verified`; **only Phase 04.3's independent isolated restore may advance to `restore-verified`**. The proposed 14 daily/8 weekly retention remains unapproved; execution additionally requires two distinct restore reports and exact plan confirmation. No schedule is installed.

Limits: logical dump is not PITR; a database-only checkpoint does not cover media; SIGKILL or power loss can leave private candidate/plaintext requiring operator review; remote deletion can fail partway and requires manual reconciliation; cryptographic key, roles/extensions, Owner MFA/auth settings and provider configuration require separate protected recovery custody. No live backup, transfer, retention or restore was performed in 04.2. Staging recoverability is still unverified.

That document defines full recovery, scoped exports, Google Drive, scheduling, retention, restore, and coverage for modules added after this Phase 04 work.
