# Data, atomic placement and API contracts

R: logical design, not migration SQL or implemented endpoints. Reuse the UUID, tenant, Kysely, exact-money and outbox conventions identified in audit E07–E18. Add forward-only migrations after inspecting actual ordered migration ledger; do not edit `1100`/`1200` or assume a migration number is free.

## Logical model

| Object | Change / constraints / access paths |
| --- | --- |
| `orders.checkout_sessions` | Extend existing table: implementation version, source kind, account owner or guest-principal binding, draft revision bigint, status, accepted quote ID, resulting Order, expiry and policy revision. Legacy rows remain distinguishable. New rows enforce exactly one owner; `CART` requires Cart reference; `BUY_NOW` has no Cart. Tenant-composite FKs for account, Cart, quote, Order. Hashes remain unique. |
| Checkout source lines | New normalized relation: tenant, draft, line ID, product/variant references, whole positive quantity and optional Cart line ID. Unique draft/variant or explicit stable configuration key; bounds from Catalog/Cart policy. Buy Now initially one variant. Store item intent; do not create inventory ownership here. |
| Quote revisions/lines | Immutable tenant/draft/revision unique, evaluated/expiry time, source/draft/config revisions, fingerprint and exact amounts; normalized quote lines/allocations, bounded JSONB for presentation/policy snapshots only. Unique quote ID belongs to draft via composite FK. Index draft/revision descending. Never overwrite a submitted quote. |
| Submission receipt | Extend platform idempotency record use with operation version and owner/draft scope, immutable canonical request digest, accepted quote and resulting Order or review result. Unique `(tenant, principal_type, principal_id, operation_type, key)` backed by PostgreSQL. `orders.orders.checkout_session_id` remains unique, cross-key invariant. Keep minimal safe outcome beyond draft expiry. |
| Order snapshots | Reuse existing Order/lines/customer/address/delivery/discount tables. Add quote/source/policy provenance and account attribution where needed. Tenant-composite FKs; immutable commercial snapshots and exact totals constraint. Corrections append history/semantic adjustment, not retroactive quote mutation. |
| Guest order access grants | New capability relation with token hash, tenant/Order, scope, expiry, revocation/rotation generation. Separate read-status vs claim-submit scope; opaque grant is not transferable to arbitrary Order IDs. Index tenant/order and active expiry; unique hash. |
| Receiving accounts/revisions | Payments-owned destinations, immutable approved revision, provider/type/public number/name/currency/status/activation; references and private verification/audit metadata. Two-person approval where available; owner exception explicitly audited. Bind intent and receipt to destination revision. |
| Claims and verified receipts | Reuse `payments.payment_attempts`, `payments.payments`, allocations and refunds. Add independent receipt source/verified time/value-date/destination and permanent receipt-key registry if existing Payment identity cannot supply immutable uniqueness. Claims can share a reference (fraud investigation), only one receipt can represent the same actual transfer. |
| Inventory allocations | Reuse reservations, allocation bridge and consumption/release semantics. Add transaction-aware batch reserve/bridge helper in Inventory instead of direct Checkout SQL. Never new Checkout balance fields. |
| Audit/outbox/projections | Existing platform tables with event schema version, aggregate revision and unique consumer receipt. Add domain event variants; no separate event bus. |

New tables use UUID keys for opaque public/domain consistency, `timestamptz`, `numeric(20,4)` and bounded text/JSONB. Core relations must not be arbitrary JSON. Decimal values and bigint revisions cross JSON as strings. Tenant-composite foreign keys prevent cross-tenant references even if an application query is wrong. Index all required referencing FKs, owner/status/updated/id lookups, expiry partial indexes, claim pending-age, destination state and submission scopes. Use `RESTRICT` for financial history; cascade only truly disposable uncommitted draft children after retention/dependency checks. Do not introduce RLS without verifying runtime roles and repository transaction context; tenant predicates and constraints remain mandatory.

Retention classes: short-lived drafts/contact details; immutable commercial/financial history; minimal idempotency tombstones; access grants; observability. Owner/legal decides durations separately. Never cascade draft cleanup into Orders, allocations or receipts. Keys must outlive every permitted retry/Worker replay; compact to a non-PII tombstone when full response retention ends. Retention must preserve cross-key one-Order binding permanently for retained Orders. Backups and restore must reapply revocations/deletion decisions.

## Final-placement transaction

1. Before transaction: schema/body size/content-type/origin validation, configured tenant, current owner authority, durable quota and feature readiness. No provider calls. Return ambiguous failures without inventing an Order.
2. Begin short local transaction. Resolve and lock the appropriate live session/guest authority revocation fence, then Checkout row. Recheck owner, tenant, generation and implementation version. All adoption/revoke/placement operations use this order; Auth logout/account revocation integration must lock the same authority before revoking. If Auth cannot participate, implement an explicit authority-generation bridge and verify its revocation ordering before enabling account placement. Browser cancellation alone is insufficient.
3. Claim submission key atomically. Replay a completed receipt **before draft expiry or source eligibility checks**, but after current authority validation. Same key/different canonical request returns conflict. Completed Order + different key returns already-committed outcome/status link without new side effects. Same-key in-flight duplicate waits only within lock timeout or receives retryable 409. Receipt never permits another owner to read the result.
4. For new work check draft active, DB-clock expiry, exact draft revision and quote revision/fingerprint/expiry. Lock Cart source if any and require its exact owner/revision. Buy Now skips Cart entirely.
5. Acquire commercial consistency fence; batch evaluate Catalog, Pricing, Promotions, Customer restrictions, geography/tariff, tax policy, payment method/destination. Use an organization-scoped shared advisory transaction lock for evaluation and exclusive counterpart for relevant commercial writers **only if all writers are migrated to the protocol**; otherwise use verified immutable active revision selection plus guarded parent rows. Price/config insert phantoms must be covered, not just locks on old rows. Keep common price evaluator authoritative. This is an implementation prerequisite, not an existing protection claim.
6. Compare complete fresh evaluation with accepted quote. If changed, persist new immutable quote/NEEDS_REVIEW and a terminal `REVIEW_REQUIRED` receipt, commit without any Order/reservation/payment/redemption. The client must generate a new intent key only after reviewing a new quote; exact old-key replay repeats its old result. Never leave idempotency indefinitely IN_PROGRESS after an intentional changed result (audit E08).
7. Lock limited coupon counters in deterministic ID order and enforce usage inside the transaction. Inventory chooses eligible locations and locks affected levels in deterministic inventory-item/location order, rechecks available-to-sell, and reserves via its own operation. Pre-sort all lines; do not let client order dictate lock order. Re-evaluate on any concurrency loss; no silent partial fulfillment/substitution. Order number sequence is taken late and may serialize tenants; measure it.
8. Create Order and immutable snapshots from **the same final evaluation**, reserve/bridge lines, commit promotion usage, create unpaid payment intent/instruction snapshot, convert accepted Cart via semantic operation, mark Checkout committed, finalize receipt and append audit/outbox. Every mutation uses the same Kysely transaction, no nested autonomous transaction. Any failure rolls all of it back.
9. Commit; return canonical Order/status grant. Grant issuance must be recoverable from receipt under owner authority if response/cookie delivery fails. Notifications/analytics/courier work starts from durable outbox only after commit.

Recommended isolation: READ COMMITTED with explicit row/fence locks and unique constraints; do not assume a transaction alone prevents anomalies. SERIALIZABLE is an alternative if the writer/fence proof fails, with bounded whole-transaction retries on serialization/deadlock. It still needs correct external side-effect isolation and unique invariants. Before implementation finalize one cross-domain lock graph covering adoption, Cart merge/conversion, cancellation, manual review, expiry, refund and inventory writers; retrofit touched conflicting paths. Do not combine independent lock orders and call them safe.

For committed Order operations the canonical local order is authority (if applicable) → Order → payment intent/claim → inventory reservation/levels → financial postings → audit/outbox. Checkout placement has no pre-existing Order row; it locks Checkout/Cart/commercial inputs before creating it. Timeout and payment review serialize on Order and intent and recheck state under lock. Lock waits and retries are bounded and observable. Preserve transaction receipt keys across retries. Database disconnect around COMMIT is unknown: consult receipt using a new connection; never unconditionally place again under a new key.

## API shape

Proposed new explicit-ID Checkout transport under existing `/storefront/v1`, using existing `{data}` / `{error:{code,message,requestId,...}}` conventions. Explicit resources distinguish tabs; IDs are not credentials. No raw owner IDs, token hashes, warehouse balances, receipt-provider secrets or CRM data in DTOs.

| Method / path | Request / result / authority |
| --- | --- |
| POST `/checkouts` | Discriminated CART `{cartId,cartRevision}` or BUY_NOW `{variantId,quantity}`; initiation idempotency key. Resolve guest/account authority; 201 draft. |
| GET `/checkouts/:id` | Current owner only; restore draft/quote eligibility/committed result, private no-store. |
| PATCH `/checkouts/:id` | `{revision,recipient:{name,mobile},delivery:{addressLine1,geographyNodeId,...},paymentMethod,couponCodes?}` allowlisted partial sections. 200 new string revision; don't accept amounts or arbitrary domain statuses. Support separate section requests with same revision semantics if useful. |
| POST `/checkouts/:id/quotes` | Expected draft/source revisions; return immutable quote, issue list and expiry; no stock hold. |
| POST `/checkouts/:id/submissions` | `{draftRevision,quoteId,quoteRevision,quoteFingerprint,termsRevision?}`, `Idempotency-Key`; 201 committed canonical receipt, 409 review/stale/key conflict, retryable conflict while pending. Bind all canonical fields plus source/payment/destination/address hashes server-side. |
| GET `/checkouts/:id/submissions/:key` | Current owner-authorized exact receipt; 200 outcome, 202 only if demonstrably durable pending, generic 404 absent. Never infer failure immediately from absent receipt while another transaction is pending; same-key POST is authoritative recovery. |
| POST `/checkouts/:id/adoptions` | Live account + current guest grant + expected revision; explicit owner change and guest revocation; no Cart merge. |
| POST `/order-access/exchanges` | One-time/rotatable link token exchange, same origin, strict quotas and no-store; issue scoped cookie; no open redirects. |
| POST `/order-access/recovery-challenges` | Tenant-scoped order reference + contact; uniform response, verified-channel challenge. No existence oracle; challenge limits and provider readiness required. |
| GET `/orders/:id/status` | Live linked account or valid scoped guest grant; limited Order/payment/delivery summary. No raw public lookup by UUID. |
| POST `/orders/:id/payment-claims` | Same authorization plus claim scope, transaction reference, optional sender identifier/claimed amount; idempotency key. 201 PENDING_VERIFICATION, never paid. |
| GET/PATCH `/account/addresses[/:id]` | Shopper account identity via Customers, pagination and revision; no arbitrary customer ID. Save requires opt-in. |
| GET `/account/orders` | Tenant/account-attributed historical Orders only, server pagination; no phone matching to grant history. |

Reference formats, maximum name/address/reference lengths, line/quantity/coupon caps use shared contracts and named server limits; align with Cart/Catalog caps in 01A. BD phone normalization accepts equivalent local/+880 forms, stores canonical form; Unicode names/Bangla address supported. Geography must be active, appropriate node type, same supported country and valid ancestry. Country initially BD only as a business policy, enforced server-side. Strict JSON schemas disallow unknown money/status/owner fields; semantic errors 422, malformed schema 400, missing identity 401, denied action 403, opaque unavailable object 404, revision/quote/idempotency 409, expiry 410 only after authorization, quota 429 with Retry-After, unavailable 503. Never leak SQLSTATE/PII. Preserve machine codes and trace IDs.

Admin transport extends existing `/admin/payments` methods/attempts/verify/reject/refund and Orders/delivery-pricing endpoints. Add destination revisions/approval, paginated exception queues, receipt-match verification and semantic correction commands. Require expected entity revision + idempotency key on financial writes. Return bounded page envelopes using existing pagination helpers; no list-all workaround. Audit authorization-denied attempts without sensitive request content.

## State transitions and authority

| Aggregate | Allowed transitions / actor / compensation |
| --- | --- |
| Checkout | ACTIVE↔NEEDS_REVIEW by owner revalidation; active→COMMITTED only placement; active→EXPIRED by DB time/Worker; abandoned by owner. Terminal cannot resume; explicit new draft. |
| Order | Existing PENDING→CONFIRMED/ON_HOLD/CANCELLED; hold→resume via Orders; completion only actual fulfillment/payment policy satisfied. Staff capability required; no Checkout patch can set Order status. Cancel creates refund obligation when paid and releases only unconsumed allocations. |
| Payment intent | READY→SATISFIED from verified allocations; READY→EXPIRED/CANCELLED from locked semantic operation; no direct “mark paid” mutation. Receipt can exist after obligation closes via exception workflow. |
| Claim | PENDING_VERIFICATION→VERIFIED/REJECTED by reviewer; ambiguous evidence remains pending/escalated with deadline. Resubmission creates history; no overwriting a rejected claim into paid. |
| Receipt | CONFIRMED→VOIDED/REVERSED only controlled correction; immutable receipt identity remains consumed. Reversal appends Finance compensation and recalculates allocations/outstanding under lock. |
| COD custody | Due→collected by courier/staff→partially/fully remitted; collection != bank receipt. Correction requires audited reversal, not a status toggle. |
| Refund | Existing requested/processing/unknown/completed/failed/cancel-before-processing. Unknown external outcome blocks blind retry; independent reconciliation resolves it. |

Financial and stock conservation assertions, replay/cross-key cases and lock-race obligations are enumerated in the [scenario register](SCENARIO_ACCEPTANCE_REGISTER.md).
