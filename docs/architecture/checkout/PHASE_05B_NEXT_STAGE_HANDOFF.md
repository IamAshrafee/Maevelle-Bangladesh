# Checkout after Phase 05B

**Storefront placement and confirmation interfaces are implemented; acceptance is PARTIAL. Public ordering, collection and production Checkout remain BLOCKED.**

The Storefront uses the three actual Phase 05A operations under `/storefront/v1/checkouts/:id`. It checks a candidate method through `POST /final-terms`, explicitly accepts the exact fingerprint from that response, submits an owner-bound request to `POST /placement` and reads private `GET /placement` status. The real development final terms operation currently returns `POLICY_BLOCKED`; this is surfaced without a Place order button. Production continues to gate the route. Do not use Admin APIs or a test policy as a storefront availability feed.

Use the same owner/draft/key/body for an unknown POST while the original tab and session live. A reload retains a bounded recovery marker only and checks authorized status without replay. A guest needs the original live Checkout authority/context plus the Order-specific HttpOnly cookie for status. Exact authorized replay can reissue that cookie; it is not reconstructed in JavaScript. If the original tab, session or grant is gone, do not promise retrieval by Order number, phone or email. Verified cross-device recovery and grant rotation require a new backend contract and privacy/retention approval.

The inline confirmation shows the immutable order reference and original terms, plus current server Order and payment status and reported balance. COD remains unpaid until collection. Fulfillment milestones and a delivery date are not supplied by this status DTO. The original total never substitutes for a live balance. Cancelled or expired payment states show no transfer action.

Before offering a customer manual transfer, add an authorized Order-specific instructions and claim contract through Payments. Define which revisions remain usable, suspension and support behavior, access scopes, claim limits, privacy retention, and independently verified actual receipts. Admin should continue using its authorized review/receipt/refund workspaces and the existing Orders/Fulfillment/COD lifecycle. No new claim, receiving number, QR, provider action, PIN, OTP, screenshot or refund path exists in the Storefront.

Activation requires approved BDT tax, invoice, fees and rounding, merchant/provider and receiving-account evidence (including Nagad), actual carrier and COD eligibility, and operating/retention decisions. Implement and authorize the real resolver separately. Before release, exercise actual browser commitment and lost-response/cookie replay, cancellation and payment status transitions, simultaneous tabs, revoked and switched accounts, proxy/cache/ingress behavior, representative load, native zoom, screen readers and physical touch devices. Do not promote prior PARTIAL acceptance or waive the historical migration byte failure based on this phase.
