**05A local acceptance: PARTIAL. Public placement and collection: BLOCKED.** This is a backend handoff; no Phase 05B UI is present. Continue to render the existing unavailable payment state. Do not mount the synthetic payment preview as a real journey.

## Transport and review

All three operations are in the existing private Checkout route scope. The production and draft feature gates still apply. The tenant is selected by the server. Keep the current shopper session and `X-Shopper-Partition`, or the guest Checkout HttpOnly cookie and its `X-Checkout-Context`. POSTs require JSON and the configured Storefront Origin. Requests do not accept client price, tax, fee, amount, destination, account, status, or address fields. Responses are private/no-store.

| `POST /storefront/v1/checkouts/:id/final-terms` | `revision`, `quoteId`, `quoteFingerprint`, `method` | New work is currently `503 POLICY_BLOCKED` after authority validation. The internal fixture-backed path requires the exact live, current, acknowledged component quote and current eligibility, then returns `CheckoutFinalTermsDto`. |

| `GET /storefront/v1/checkouts/:id/placement` | Authorized draft ID; guest also needs the Order cookie | `{data:{receipt,status,payment:{status,outstanding}}}` for a committed authorized Order; `404` for missing ownership, binding, or guest grant where applicable. Session and production gates still apply. |

The component quote remains unchanged: tax, fees and payable are null; `final`, `purchaseAvailable` and `stockReserved` remain false. When a real policy is approved, the **separate** final-terms DTO carries BDT, the reviewed components, exact tax and its treatment, fees, explicit rounding, zero merchant wallet surcharge, payable, selected method, quote/root references, expiry and a fingerprint bound to the actual method, destination, operating and commercial policy revisions. Render values as server decimal strings. Read item discounts and allocations from the immutable component quote referenced by the final terms. Final acceptance means an explicit submit using the exact displayed final fingerprint; a component acknowledgement is insufficient. On `REVIEW_REQUIRED`, restore current owner/source/delivery/quote, re-review and use a new intent key for the new acceptance. No automatic replacement quote is generated.

## Receipt and recovery

- The receipt contains Order ID, Order number and the committed final terms. The status operation adds live Orders and Payments status and outstanding amount. The immutable receipt payable is the original amount; current outstanding can change. A cancelled or expired obligation should never prompt a new transfer. A committed Order is never proof of paid funds.
- An account uses the same live authenticated account and current partition; the draft has immutable attribution after commit. Recipient phone does not grant Order access. The read works after draft expiry while the account remains eligible to access it.
- For a guest, successful placement or exact replay issues an HttpOnly, SameSite=Lax, one-hour cookie scoped by draft ID in its name. The underlying grant is Order-specific, hashed at rest and expires no later than its original Checkout session. The status operation also requires that session and its context. Logout/revocation/session expiry cannot be bypassed using the grant. The existing development setup uses the same local cookie conventions as Checkout; production routes remain disabled. Keep grants out of URLs, JSON, client stores, logs and analytics.
- On ambiguous placement failure, keep the same key, body and owner partition. Replay the original POST even after draft expiry or Cart conversion; it reconstructs the original receipt and guest cookie after commit. Do not create a second draft, generate a fresh key, or infer success. If the guest Checkout session is gone, verified cross-device or staff-assisted recovery is unavailable. Independent grant rotation and longer guest retention need policy and implementation.
- COD uses an unpaid collection obligation. Manual placement uses an unpaid obligation with private revision-bound instructions and expiry internally. This phase exposes **no** shopper instructions, claim submission or proof upload endpoints. A manual claim cannot be treated as verified money. No public receiving number, transfer or PIN/OTP workflow is available.
