## Authorized operator sequence

1. **Read-only preflight.** Once authorized, use `pnpm staging status --host APPROVED_ALIAS --engine podman` and `pnpm staging plan --sha FULL_CANDIDATE_SHA --host APPROVED_ALIAS --engine podman`. These contact SSH and GHCR. Compare target record, approved release and running digests. Inspect the ledger prefix and object compatibility against the exact predecessor, including historic drift. A pending-migrations refusal is expected on ordinary deployment when the target is behind. Resolve cutover with the operator.
2. **Backup and validate recovery.** Use the existing scoped PostgreSQL/media backup procedure after authorization. Record IDs, timestamp/LSN where available, checksums, digests and ledger. Restore into an isolated nonproduction target and verify schema, finance/Order/stock/outbox totals, media, permissions and measured recovery. Keep source databases/media intact. Define post-backup reconciliation before migration. The local rehearsal does not establish this target backup.
3. **Quiesce and migrate.** Obtain separate cutover approval for exact host/database, pinned API image, predecessor and target suffix, writer downtime and repair. Hold timer and active rollout. Stop/fence incompatible Maevelle writers/jobs, verify no remaining write path and keep PostgreSQL/media/Caddy persistent. The restricted operator gateway does not expose cutover. The [migration helper](../../../scripts/staging-migrate.sh) supports `status`, `preflight` and `apply` with a pinned digest and protected environment. `apply` requires `--confirm maevelle_staging`. See the existing handoff for the reviewed command template. The helper locks migration. The operator establishes backup, writer quiescence and cross-operation serialization. Apply once, check ledger and objects, stop on error. No reset, automatic seed, startup migration or volume deletion.
4. **Deploy compatible services.** Before writer restart prove the allowed image/schema pairings for the target and interruption states. Cover Checkout financial projections, privacy proof, session/Cart credentials, outbox/Worker and both UI contracts. Coordinate all four images for this backend change. Existing orchestration stops Worker, updates API/Admin/Storefront, then starts Worker. Keep count-based and sequence-based Finance writers from overlapping without proof. Preserve transaction-backed per-organization/document numbering. After separate authorization use existing `pnpm staging deploy` and `pnpm staging verify` with approved SHA, host and engine. Retain attempted/current/previous releases and running digests.
5. **Verify disabled staging.** Check ledger, units, API `/health/live` and `/health/ready`, Worker progress, HTTPS routing, `/admin` and Storefront, auth realm/callback/2FA, host-only Secure cookie issuance/clearing where applicable, Origin/Fetch Metadata, spoofed forwarding, direct API denial and private cache. Verify purchase/collection, adjustment application, live payouts and optional dispatch remain disabled. Private Checkout namespace rejection is expected in current production mode. Record it as such.
6. **Reconcile and record.** Within authorized synthetic scope, independently check Order/obligation, receipt/allocation/refund/ledger, stock/promotion/Cart conservation and courier collection/custody/remittance separation. Check Worker replay/poison/backlog, duplicate suppression and redacted diagnostics. Use synthetic canaries across app, gateway, trace, metric, error, dead-letter, cache/history and support sinks. Record actual results, exceptions, operator/time, digests, config revisions, ledger, backup and holds. Four successful Checkout paths require their own fixture or approved policy.

## Abort and recover

- Abort before mutation on host/database/ledger, artifact/digest, secret/egress, writer, backup or recovery mismatch. Stop on failed migration, wrong/unhealthy unit, private data leak, broken revocation, unintended send or purchase, numbering collision or cash/stock/Order variance. Preserve logs, manifests, timestamps, hashes and restricted diagnostics. Notify the named incident commander and Finance/Security leads.
- If migration succeeds and deploy fails, hold incompatible writers and automatic rollout. Compare the resulting ledger. Roll images back only to pinned versions proven compatible with resulting schema, numbering, credentials and consent. Gate 0 has no verified fallback. Otherwise repair forward under approval. Do not down-migrate financial records.
- If separately authorized restore is necessary, coordinate PostgreSQL/media and reconcile post-backup receipt/refund, provider uncertainty, Order/stock/outbox, credential revocation, consent withdrawal and deletion requests before writes/dispatch resume. Earlier restore rehearsal demonstrated stale grants/consent can reappear without reconciliation. Preserve authoritative history and avoid duplicate payouts.
- Resume after independent verification and recorded approval. Timer re-enable, host ingress changes and commercial activation have distinct authorization boundaries.
