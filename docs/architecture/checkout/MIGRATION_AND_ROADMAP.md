# Legacy replacement, compatibility and A/B roadmap

R: implement only after a separate assignment. This document does not authorize Phase 01, live target inventory, migrations, deployment or payment operations. Each capability follows Backend A → Frontend B → integrated acceptance against the real backend. Security belongs in each phase. Phases may be worked internally in increments but cannot be called complete while important surfaces remain missing.

## Replacement and migration strategy

1. **Inventory consumers before editing:** locate all Checkout imports, route consumers, cookies, Admin/manual Order dependencies, notification templates, reporting queries and migration fixtures. Preserve current Git changes. On an authorized target later obtain schema ledger/version, row counts/state cohorts and pending financial obligations without exporting PII. Current deployed versions/data are NOT VERIFIED.
2. **Expand schema, keep readers compatible:** new forward migrations add owner/source/implementation-version, quotes, grants, destination revisions and receipt provenance. Preserve existing order IDs/numbers/snapshots, receipt references, outbox IDs, Finance/Inventory bridges. Do not backfill account ownership by phone. New table/column readers tolerate legacy rows. Backfill batches are resumable, tenant-scoped and checked against counts/financial conservation. New constraints validated after diagnostics; failures stop migration rather than deleting “bad” history.
3. **Reader-first deployment:** compatible API/Worker/Admin reads both versions and honors permanent credential retirement. Deployment preflight identifies exact old/new image compatibility and ledger. Don't allow old placement code to write rows with new semantics. Use maintenance/write fence for incompatible paths; feature gate new initiation/submission until all required readers/writers/policies are ready. Existing status/payment claims for committed Orders remain safely supported.
4. **Classify legacy drafts:** unplaced draft remains legacy until expiry, or explicitly restart after owner-authorized source review. Do not transform a guest Cart checkout into account/Buy Now merely because session exists. Existing committed Orders keep hardened scoped legacy confirmation access until reissued grants or verified recovery. Current one-hour browser cookie is not the retention policy for financial evidence.
5. **Cut over writers:** new source creation and submissions use new shared DTO/API; Storefront/Backend/Worker switch with capability flags and protocol version. Replace old `/current` mutation routes with fail-closed unavailable/restart responses for old clients; do not keep a weaker parallel checkout path. Preserve exact old committed receipt access only under new tenant/grant controls. Re-scan consumers before retiring exports.
6. **Historical Payments:** preserve original instruction snapshots and references even if receiving account unknown; mark legacy provenance unverified. Never invent approved destinations or independent receipt matches for old rows. Duplicate/reversal identity backfill quarantines ambiguity for operator review. Financial truth is reconciled through semantic corrections, not destructive deduplication.
7. **Retire later:** remove demo hook/runtime fixtures/unused CSS only after import/build/browser compatibility evidence. Keep historical migrations, Orders columns/FKs and old event-version readers as long as retained outbox/records need them. Contract-removal migration is separate, justified and reversible through compatible readers or forward repair; no broad cleanup during initial replacement.

## Deployment and recovery

Reuse CircleCI/GHCR, immutable full-SHA/image digest manifest, Maevelle-only rootless Podman/Quadlet service group, persistent PostgreSQL/media and private Caddy/Nginx. Apply pending forward migration suffix exactly once in controlled job, never concurrent API/Worker startup. Existing release executor/ledger requirements must be reconciled with actual schema before rollout. Do not modify unrelated host applications, shared Nginx/OS, public DB exposure or volumes.

Before each schema change record last release compatible with resulting schema and forward-repair/verified backup plan. New data semantics may make an older image incompatible even when columns are additive. Gate/stop incompatible writers, capture backup/media and diagnostics, migrate, deploy compatible readers/Worker before enabling new writes. Existing operations must continue through compatible images or a short explicit maintenance window. Failed ledger/health/smoke check stops rollout and retains manifests/logs.

Rollback means gate new submissions and use only images/config proven compatible with resulting schema and revocation rules; keep committed Orders/status/claims/settlement available safely. Never reverse applied migrations or restore history just to undo UI. If incompatible, repair forward; database restore is an independently authorized recovery operation with reconciliation of all writes and provider side effects since backup. Restore offline, reconcile revocations/deletions/receipt IDs/outbox effects and customer/payment history, then reopen. A pre-credential-retirement image/backup must never re-enable old bearer access. Real target restore/ingress/provider checks are release gates, not Phase 00 results.

## Per-phase execution discipline

Each A phase delivers focused domain files, contracts/permissions/migrations, security assertions and meaningful tests; each B phase uses shared primitives and real response/error semantics, not demo success mocks. Every exit records source commit, narrow checks actually run, integrated scenario evidence, latency/query/queue impact, operation/retention changes and remaining risks. Refer to scenario IDs rather than copying their prose into repeated reports.

Performance: 01 ownership lookups indexed and quotas bounded; 02 geography paginated/cancellable; 03 batched evaluation and immutable revision reads; 04 financial queues indexed and timeouts bounded; 05 critical transaction duration/lock graph; 06 server-side paginated operations; 07 async exports/projections; 08 representative measurement; 09 shared-host rollout overhead. A green unit/type check alone closes none of the corresponding runtime gates.

The exact safe next assignment is **Phase 01A backend only**: verify baseline/dirty state, finalize lock/authority/source and receipt contracts against current Cart/Auth/Orders/Payments, add forward schema + shared DTOs + strict owner-scoped draft/initiation APIs and focused isolated ownership/upgrade tests. Keep Checkout purchase gate off. No Phase 01B, payments activation, live migration or deployment implied.
