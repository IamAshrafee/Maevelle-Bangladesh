# Phase 02 migration tooling

Status: implemented locally; not activated on the VPS. The 51 migrations at `ccd405c1e6fa8c827307977b947a4a3dbce859f5` are the immutable source baseline. This phase changes no historical migration file and performs no staging database operation.

## Developer and CI commands

| Command | Purpose |
| --- | --- |
| `pnpm check:migrations` | Verify historical SHA-256 checksums, source/registry mapping, identifiers, duplicates, and that new migrations sort after the baseline. No manifest is generated by this command. |
| `pnpm test:migration-policy` | Test acceptance of a registered new migration and rejection of changed/deleted history and registry/file mismatches using temporary copies. |
| `pnpm exec vitest run packages/database/src/migrate.test.ts` | On a configured PostgreSQL 18 `TEST_DATABASE_URL=.../maevelle_test`, create a disposable database and test fresh installation, complete ledger, schema objects and idempotent rerun. |
| `UPGRADE_TEST_ALLOW=1 TEST_DATABASE_URL=.../maevelle_test pnpm test:migration-upgrade` | Create a separate disposable database, migrate to the 51-name baseline, insert representative organization, numbering and configuration records, run new migrations, verify preservation and rerun, then drop it. Never point this at VPS. |

The upgrade harness rejects every post-baseline migration without a corresponding `UpgradeCase` in `packages/database/src/upgrade-cases.ts`. A case creates migration-specific pre-upgrade state and verifies its intended post-upgrade result. Add meaningful data transformation, defaults, constraints, index or relationship assertions appropriate to that migration. The current harness reports **no post-baseline migration exists**; its successful run proves the framework and baseline-data preservation, not a future breaking migration. Keep upgrade cases focused rather than growing a generic test matrix.

`packages/database/migration-history-baseline.json` records SHA-256 hashes of the 51 current `.ts` files; the validator also anchors the reviewed manifest digest. The validator never rewrites either value. An exceptional history rebaseline requires inventorying every applied ledger and schema, deciding explicit forward reconciliation or authorized resets for each environment, verifying backup/restore, rebuilding and checking fresh and upgrade paths, then reviewing a new baseline manifest, digest and release reference together. Never regenerate the manifest merely to quiet a failed check.

## One-time staging command contract

`scripts/staging-migrate.sh status|preflight|apply --image ghcr.io/iamashrafee/maevelle-api@sha256:<64-hex-digest> --env-file /home/maevelle/deployment/secrets/staging.env [--confirm maevelle_staging]`

The script is intended for the rootless `maevelle` user on the VPS. It checks the private network and running PostgreSQL container, verifies that the protected `DATABASE_URL` targets `maevelle-staging-postgres/maevelle_staging`, validates migration history **inside the selected API image**, and shows the Kysely ledger. All actions take a nonblocking `flock` at the Maevelle user runtime directory; `status` and `preflight` require the selected image to be present locally and do not pull it. `apply` additionally requires the exact confirmation string, may pull the image, invokes the existing compiled Kysely CLI once, and shows final status. It never sources or prints the environment file, starts Owner bootstrap/seed, resets data, or restarts services. The API image now includes the validation script, manifest and migration sources alongside its compiled CLI.

This lock path is shared with the Phase 03 deployment executor for deployment-level serialization. The installed deployment tool's read-only `status` passed on the VPS; the migration runner itself has not been activated or verified there. A successful migration does not declare the application release healthy or provide database rollback.

## CI path

The existing CircleCI `main` publisher remains the only automatic image publisher. Its script builds the same four images, then runs the history validator and policy tests inside the API image before publishing. On its disposable PostgreSQL 18 container, it runs the existing Vitest fresh-install test, the new upgrade harness, the existing compiled migration CLI, and the API startup check. Any failure stops before GHCR pushes. No automatic VPS deployment is added. CircleCI uses the same synthetic credentials already generated for its disposable PostgreSQL; neither tests nor logs require staging secrets.

## Remaining activation gates

Verify the actual rootless Quadlets, protected env path and image runtime on the VPS read-only; confirm that the image's digest and migration source match the intended release; share the lock with the later deploy command; rehearse failure handling and database/media backup/restore on an isolated target; and test a real post-baseline migration with representative upgrade data before allowing the one-time runner to modify staging. Application rollback remains separate from schema recovery.
