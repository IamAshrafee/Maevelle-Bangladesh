# Phase01A implemented guest bootstrap protocol

Backend D15 is resolved for the new slot protocol by actual PostgreSQL/API tests in `apps/api/src/cart-foundation.test.ts` (S01–S05/S17/S35–S38/S59). Real-browser cookie behavior remains a distinct Phase01B gate. This document supersedes the fixed-cookie recommendation for newly issued credentials; it does not claim that two anonymous requests can be identified as the same browser.

## Protocol

1. GET `/storefront/v1/carts/current` with no credential returns 404 NOT_FOUND and never creates a Cart. An explicit POST `/storefront/v1/carts` with `{}` resolves configured organization/currency and strict shopper identity. Legacy organizationId/currency fields are accepted only as checked assertions.
2. Each independent cookie-less initializer creates an empty existing `cart.carts` row and issues a **different cookie name**: production `__Host-maevelle_cart_<server-cart-uuid-without-hyphens>`, localhost `maevelle_cart_<slot>`. Value is random 32-byte opaque credential; only its hash is stored. Slot/public Cart UUID is not a credential.
3. Cookie is HttpOnly, Path=/, SameSite=Lax, 30-day existing lifetime, Secure/host-only in production. No bootstrap response sets authentication cookies, overwrites another guest slot or reissues the legacy fixed cookie. No token appears in response DTO, logging or URL.
4. Mutation must return a valid issued cookie. The initial response itself contains no credential for JavaScript to echo. A request that outruns cookie establishment or whose browser rejected Set-Cookie receives 409 SESSION_ESTABLISHMENT_REQUIRED and causes no merchandise writes. New clients must observe the issued cookie in a subsequent request before treating the session as established.
5. One valid scoped cookie gives one guest owner. Multiple valid cookies with no explicit selector return 409 CART_CONTEXT_REQUIRED with only cookie-authorized public ownerContext references. `X-Cart-Context` or body ownerContext selects a context **only when its credential is also present**. Conflicting selectors return OWNER_CHANGED. No selection, copying, merge or ownership transfer is inferred.
6. An initializer with established selected authority returns its current Cart with 200 and **no Set-Cookie**. Independently duplicated initializers without credential are not falsely deduplicated by IP/key/fingerprint: they can create separate empty contexts. A received cookie plus lost JSON is recovered by GET/repeated initialize. A completely lost cookie response leaves only an unacknowledged empty row.
7. Modern mutations send ownerContext + numeric version + UUID Idempotency-Key; an old prepared request with a new cookie and old context fails before writes. Ambiguous legacy requests fail rather than guessing a Cart. Account resolution errors/expired cookies never become guest initialization. Verified account Cart operations deliberately return ACCOUNT_CART_NOT_READY until the account capability is implemented.

## Controlled-order proof

Test sequence: start cookie-less initializers A and B concurrently; deliver A cookie only; acknowledge add A; deliver B cookie late; verify jar retains both names; unqualified read/write refuses; explicit cookie-backed A read retains the acknowledged unit and explicit B read is empty. Another test acknowledges independent adds in A/B and then retrieves both exact quantities from the combined jar. Tests also prove cookie-free add refusal, initialization cookie reuse/no reissue, lost responses, UUID-only denial, forged token denial and owner change rejection. These are deterministic API cookie-jar simulations using real database transactions, not real browser verification.

## Phase01B contract and limits

Use single-flight/Web Locks as usability coordination, never server authorization. Persist only public selected context and pending intent metadata, no token. On CART_CONTEXT_REQUIRED, read each explicitly authorized context and ask the shopper to select/review; do not automatically merge or erase another acknowledged Cart. Keep pending operations bound to their original context, key and body. A deferred initialization response must not trigger a new active-context switch. Resolve unknown outcomes by exact same-key/body retry before inventing another intent.

At most 32 supplied credentials are inspected; a larger header is refused, never evicted by server cleanup. Creation quota is 20/minute per direct-IP/storefront key; requests with recognized authority issue no new cookie. Browser cookie quotas, deliberate cookie clearing/eviction and cookie rejection cannot guarantee restoration: acknowledge only server-committed operations and expose persistence limits truthfully. Expired or foreign capabilities return SESSION_EXPIRED; full session restoration/rotation/cleanup belongs to Phase03.

## Legacy compatibility boundary — not closed

The original `maevelle_cart` bearer cookie remains accepted and is never rewritten during bootstrap. It lacks the modern __Host naming protection. Full old-cookie retirement/dual-credential rotation and complete owner-precondition parity for old clients are **not implemented**. A public intent/Cart ID cannot replace proof, and rotating/revoking an acknowledged legacy credential before a replacement cookie round trip would reintroduce lost-Cart risk. Do not call this full legacy session-fixation closure.

Legacy no-key mutations derive a receipt identity from canonical operation/version/payload and are supported only for one unambiguous credential context. Existing Checkout parses one new slot as well as the old cookie and refuses multiple slots rather than guessing. Signed-in legacy Cart requests now receive explicit ACCOUNT_CART_NOT_READY instead of silently continuing anonymous authority; this is a known compatibility gap, not an implemented account Cart. Both gaps keep Phase01A overall PARTIAL. Smallest closure: an owner-reviewed legacy compatibility/credential-adoption protocol with loss/reordering/retirement tests, followed by Phase01B owner-aware client adoption; account ownership/merge remains separately scoped Phase03.
