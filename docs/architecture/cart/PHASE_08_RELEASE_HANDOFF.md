# Cart Phase 08 release handoff

**Decision: BLOCKED.** Local ingress fixes are verified. Persistent recovery, actual ingress and operational controls, owner approvals, and human acceptance remain open. The [Phase 07 report](PHASE_07_RELEASE_READINESS.md) holds the earlier restore and Cart integrity evidence. The VPS Nginx vhost and live Quadlet definitions are outside this checkout.

## High defects fixed locally

- **Shared gateway quota.** A second client behind the same API socket peer got 429 after the first exhausted its Cart creation allowance. Caddy now overwrites `X-Maevelle-Client-IP` with its resolved client address. The API accepts a single literal address from exactly the configured Caddy socket peer, normalizes IPv6 and mapped IPv4, ignores the header from other peers, and fails closed on missing or malformed values from the configured peer. The change covers durable Cart and Shopper Auth quotas. Fastify's global proxy trust stays off, so this change adds no authority to forwarded Host or scheme. Unrelated in-memory limiters, including first-party observation ingestion, still use the socket peer and need separate volume validation.
- **Gateway error logging.** An isolated Caddy 502 disclosed a synthetic reset URL. The Caddy runtime log filter now strips structured request URIs, request headers and response headers while preserving error diagnostics. Phase 07 already redacted the API's Shopper Auth request logging. Historical logs and the actual Nginx vhost still need separate verification.

## Release gates and operator procedure

1. **Critical — Exact persistent upgrade and revocation continuity.** Record the authorized host, Maevelle user, database identity, ordered Kysely ledger, running schema and previous image digests. Compare the ledger with the target manifest. Stop if it diverges or the actual schema or row constraints differ. Rehearse from an encrypted, checksummed database backup and matching media snapshot in quarantine with public traffic, provider delivery and background side effects disabled. Record restore duration, tolerated data loss, active Account Bag continuity, guest credential states, retained lines/coupons, receipt counts and pending/completed/dead-letter counts. Verify runtime grants separately since an isolated fixture owner does not represent production roles.
2. **High — Actual ingress and historical exposure.** In the Maevelle-only HTTPS vhost, replace incoming `X-Forwarded-For` with `$remote_addr`, replace forwarded Host and scheme with the approved host and TLS scheme, and clear any caller-supplied `X-Maevelle-Client-IP`. Review Nginx real-IP rules first so `$remote_addr` cannot be caller-controlled. Set Caddy's `MAEVELLE_NGINX_PEER` to the observed immediate Nginx peer as a single /32 or /128 and the API's `API_TRUSTED_GATEWAY_IP` to the observed Caddy peer as a single literal IP. If Podman masks the ingress peer behind a shared address, prove the trusted path is exclusive or use a dedicated ingress listener before enabling trust. Confirm the loopback Caddy bind, no public API/DB ports, and no untrusted workloads able to originate from the trusted peers.
   - On authorized staging, exhaust a Cart quota using one synthetic client and confirm a second independent network client remains eligible. Repeat with forged and repeated forwarding headers and on a Shopper Auth route. Check direct backend reachability externally and verify source stability after unit recreation. Confirm TLS, HTTPS redirects, `/admin` and callbacks, Cart/auth private no-store, production cookie scope and flags, foreign Origin rejection, account switching, and Admin denial without `analytics.view`.
   - Send synthetic token, coupon and header canaries through successful, rejected and upstream-failure paths. Search authorized API, Nginx access/error, Caddy, rotated archives and trace sinks in place. For the historical exposure window, record affected route, deployment dates, counts, sinks, retention and who could read them. Keep raw values out of tickets and chat. If exposure is confirmed, have the incident owner establish whether capabilities were still live or used. With separate authorization invalidate affected live capabilities, reissue as needed, revoke affected sessions when warranted, and record impact and log disposition. Nginx error logs require their own canary because access-log formatting alone does not govern them.
3. **High — Runtime permissions and recovery.** Verify scoped API/Worker roles can execute their workflows, cannot perform DDL or access unrelated schemas, and are distinct from the migration role. Verify restricted secret storage, the dedicated rootless network and volumes, `/api/health/live` and `/api/health/ready`, restart policies, and actionable 429/503, lock, pending-age and dead-letter alerts. Restart the Worker against an authorized synthetic backlog and confirm it drains with one fact per outbox ID. Investigate a dead letter before any replay.
4. **High — Owner decisions and acceptance.** Record approver, date and selected option for each launch-blocking row below. Run one authorized mixed workload using projected volumes for Cart mutations, merge, Wishlist Move, reports and Worker lag. Capture p95, pool waits, SQL locks/deadlocks, 429/503 and backlog age against agreed thresholds. Complete iPhone Safari, Android Chrome, tablet portrait/landscape, desktop Safari/Firefox, keyboard and native zoom, VoiceOver and TalkBack or NVDA. Check focus return, status announcements, touch scrolling, sign-in/account switching, and recovery from interrupted merge and Wishlist Move. Device and real-edge checks are pending.

## Controlled deployment and recovery

- The manifest must identify the exact commit, API/Worker/Admin/Storefront digests, compatible prior digests, expected ledger, and Caddy config revision. The existing release executor requires an already-matching ledger. Coordinate any approved schema job separately from application rollout. Rehearse using the same image and migration role before touching the persistent target.
- Quiesce Maevelle writers and checkpoint database/media before a needed migration. 3213 scopes foundation data, 3214 permanently retires legacy bearer hashes, 3215 checks legacy data against integrity constraints, 3216 enables account ownership, and 3217/3218 enable projection and observations. Apply the pending suffix once. Stop on migration, health or smoke failure and retain SQLSTATE, ledger, unit diagnostics and manifest. Repair forward on a clone first. Once schema is ready, coordinate the Caddy/API trust settings under the maintenance gate, then use the manifest-driven application rollout. Verify receipt replay, revocation, reporting and Worker progress before opening traffic.
- For rollback, select only image/config versions verified against the resulting schema and current revocation rules. A pre-3214 restore stays offline while the migration is reapplied. Later snapshots can also restore credentials revoked after the backup. Reconcile revocations, deletions and sessions from authoritative records before reopening. If guest revocation history is incomplete, obtain approval to retire every restored active guest slot using a reviewed forward operation and verify old tokens fail. That fallback preserves history but resets guest Bag access. Never reverse 3214 or expose the restored snapshot while continuity is uncertain. Reconcile post-backup writes and provider side effects, retain receipt/outbox linkage, and record actual recovery time and loss.

## Local verification

Six focused API/config tests passed, covering quota isolation, spoof resistance, origin, secure guest cookies, durable counters and Shopper Auth log safety. The API typecheck, API build and whitespace check passed. The Caddy check used 2.10.2 on an internal Docker network with a synthetic trusted peer and echo backend. It verified two distinct forwarded addresses, ignored spoofed claims from an untrusted peer, and confirmed the 502 diagnostic survived with its canary removed. The local topology did not include the host's Nginx or Podman network.

The legacy migration fixture upgraded populated intent through 3213 and the current ledger, retained Cart lines, coupon scope and receipts, and denied the old bearer. Phase 07's isolated backup/restore remains the prior restore evidence.

A local PostgreSQL 18 sample ran 50 guest reads, 20 year-window reports and two consumers against 10,000 projected facts and 1,000 pending events. Observed p95 was 10.76 ms for the read, 40.63 ms for the report and 24.71 ms for the batch. The backlog drained in 66 ms with no sampled lock waits or processing errors. Eight opportunistic activity samples saw at most one other active statement and give no reliable saturation estimate. This direct database fixture did not exercise network/auth costs or mix in Cart/merge/Wishlist writes. Production capacity remains open.
