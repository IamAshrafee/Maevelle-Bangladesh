## Account Wishlist transfer

Account Wishlist and Account Cart already share a PostgreSQL database. A transaction avoids the ambiguous intermediate state that would result from issuing an ordinary Cart add and a separate Wishlist delete. The new protected Cart endpoint invokes the existing receipt engine, the same Cart line-add operation as PDP and the existing Wishlist removal operation. It uses the same Cart outbox event. There is no schema migration, worker, or second receipt table.

The command resolves the shopper once through the existing Cart route. Within the transaction Cart checks customer and account authority using the existing customer-before-account locking sequence, locks the Cart, resolves the receipt, and checks the Cart revision. A fresh transfer then locks the account's Wishlist list by tenant and account and checks its revision and saved item. Existing private Wishlist writers serialize on that same list. Cart is the only new predecessor of the list lock. Ordinary Wishlist writes and share management do not acquire a Cart lock. The transfer takes no additional identity lock and does not call Shopper Auth or the Wishlist route from inside the transaction. This source review and the held-lock guest-discovery regression leave broader deployed contention verification open.

A saved exact variant must match the submitted variant. For a saved product without a preference, the shopper explicitly chooses a variant from the same product. Catalog checks variant ownership, active publication and structural option integrity. Cart checks consolidated quantity, stock and price, and evaluates the resulting Cart under the same repeatable-read transaction. **ADD** preserves the Wishlist entry. **MOVE** removes it and advances the Wishlist version only after Cart accepts the exact addition. A failure in either operation, the outbox write or receipt persistence rolls back the transaction. Cart stock and benefit previews can change after commit.

Two matching submissions converge on one receipt. A distinct request on the old Cart revision receives a conflict. A changed Wishlist revision also rejects a fresh request. Replays validate the current Cart authority and receipt identity before checking either revision or source membership, so a committed Move remains recoverable after the source entry has disappeared. Replays return the historical outcome alongside the current evaluated Cart. A saved item subsequently added back to the Wishlist is independent of the earlier Move.

## Guest, shared and recommended products

- **Guest Add — supported through the existing exact Cart line endpoint.** The guest Wishlist is a browser journal. Establish and select the intended guest Bag independently, confirm a public configuration and keep the saved entry. Guest Move remains **PARTIAL**. A backend transaction cannot include the browser journal. Enable Move only after implementing durable exact Cart intent recovery plus coordinated, conditional journal removal of the same saved generation. An owner change or intervening edit must preserve the current saved item.
- **Shared recipient Add — supported as a public Catalog continuation.** The existing share lookup checks tenant, token, revocation, expiration and current public visibility. Existing recipient Save copies a product from the opened view into the shopper's own Wishlist workflow. Account Save checks current Catalog eligibility. Revoking the share blocks reopening it, while a previously received public product ID can still be saved independently. For Cart, a valid shared view can take a recipient to the public PDP or exact variant picker. Submit the normal Cart add under the recipient's independently verified guest or account authority. Share and management credentials never enter Cart. An expired or revoked view should hide share actions after revalidation. A public PDP already reached from that view remains independently accessible, and an exact Cart retry remains tied to its original owner. The Cart API provides no share-scoped mutation, source removal or bulk operation.
- **Recommendation Add — supported through the existing PDP and exact Cart line endpoint.** The current Recommendations evaluator provides bounded `pdp_complementary` and `pdp_similar` placements with public Catalog eligibility and availability filtering. A result can become stale. Resolve current options, submit only the selected variant and quantity, and handle the same current Catalog, stock and pricing errors as any other Add. Recommendation failures stay independent of Cart discovery, mutation and recovery. Bag-specific ranked placement remains **PARTIAL**. If added, it belongs to Recommendations with bounded seed and exclude sets and a single independently failing request. The current PDP endpoint should not be called once per Cart line.
- **Bulk and reverse transfer — open.** This assignment implements single-item Wishlist-to-Cart. The roadmap's shared bulk and Cart-to-Wishlist paths still require distinct contracts. A bulk design needs a reviewed limit, per-item results and stable item operation identities. Cart-to-Wishlist needs save-first recovery fenced against newer Cart line edits.

## Commerce behavior

The same Cart projection reevaluates current prices, fixed-point amounts, stock, selected coupons and discount allocations after transfer, including after consolidation. The existing Promotions evaluator applies supported schedule, targets, merchandise thresholds and stacking rules. A selected coupon can have zero current benefit. Cart uses the existing public preview policy for both guest and account, so customer-limited redemption eligibility is not inferred from sign-in. The receipt records the committed intent revision and line changes. The calculation fingerprint identifies the current evaluation and can change independently as prices, stock or promotions change. Purchase-time redemption remains with Checkout and Orders.

## Phase 04B contract

1. For a private Account Wishlist action, use `POST /storefront/v1/carts/account/current/wishlist-transfers` under the existing same-origin API proxy. Send JSON `WishlistCartTransferRequestDto` with `action` (`ADD` or `MOVE`), `productId`, explicit `variantId`, `quantity` (whole units as a string from 1 through 99), the observed `wishlistVersion`, and the observed Cart `version` and `ownerContext`. Use the Account Cart session and shopper partition, and a UUID `Idempotency-Key`. If sending `X-Cart-Context`, it must agree with the body.
2. Extend the existing Cart controller intent and pending-journal union. Capture the source revision and configuration at confirmation, serialize with other Cart commands, and pin the full body, endpoint, owner and key for replay. Treat a disconnect, timeout or uncertain server error as unresolved. Retry the identical submission against the same owner within the existing seven-day receipt window. On owner change or receipt expiry, refresh and reconcile before offering a new customer action.
3. Success is `{ data: AccountCartViewDto }`. `outcome.operation` is `wishlist_transfer`. Match the response to the submitted action, use `outcome.changes` and `committedVersion` as the receipt, and render the returned Cart as the current projection. Refresh the private Wishlist after Move, including after replay. Never issue a separate source deletion. Render selected coupons from `commerceReview.coupons` and its `EFFECTIVE` or `NO_CURRENT_BENEFIT` status. Read line availability from the current projection.
4. `WISHLIST_CHANGED` and `STALE_VERSION` (409) require a refresh and review. `OWNER_CHANGED` fences an old context. `IDEMPOTENCY_CONFLICT` indicates the transfer key was reused with a changed body. `NOT_FOUND` covers an absent source. `INVALID_CONFIGURATION` requires current options or updating the saved exact variant. `UNAVAILABLE`, `UNPRICED` and `LIMIT_EXCEEDED` leave the saved entry intact. Avoid silently substituting another variant or rebasing a rejected transfer.
5. For a guest saved item, shared-list recipient or recommended product use the existing guest or account `POST .../current/lines`. This action keeps the source saved and requires an exact current public variant. Bind recovery to the selected Cart context, especially where multiple guest Bags coexist. Keep optional discovery and share failures isolated from the Bag.

## Verification and remaining gates

The Fastify suite runs against fresh PostgreSQL 18 databases with real shopper verification and sessions. It exercises Add followed by Move, variant consolidation, same-key races, changed-body rejection, stale Cart and Wishlist versions, cross-account denial, insufficient stock, and outbox failure after source removal. The outbox failure fixture retries the same body and key successfully after removing the test-only constraint, establishing rollback of the source deletion, Cart mutation and receipt claim.

The transfer adds one tenant/account list lookup and one tenant/list/product lookup on fresh commands, both backed by existing unique indexes. Move adds the existing deletion, list revision update and Wishlist outcome recording. Replay skips source queries. These are query-shape observations, with no transfer latency benchmark, representative workload or production capacity measurement.

Phase 04B browser integration, guest Move, shared bulk, reverse transfer and Bag recommendation ranking remain open. Phase 03D.1's persistent cutover, backup, restore, revocation, deployed proxy/TLS/roles, retention and deletion, quantity and destination policies, advanced promotions, tax and compare-at, representative workload and physical-device/accessibility gates remain separate.
