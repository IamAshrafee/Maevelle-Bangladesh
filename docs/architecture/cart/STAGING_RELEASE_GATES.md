# Cart staging release gates

**BLOCKED for release and for a persistent-data rehearsal.** The repository's local recovery evidence supports preparing an isolated rehearsal. Starting one with a staging backup requires a verified source, an approved quarantine target, and explicit authorization to retrieve and restore that backup.

## Verified in this review

- Git HEAD is `8138746ea20af613e9a34265a19c278b8beb89d6`. The working tree already contained the Phase 07 and 08 fixes. Preserve those changes and identify an immutable candidate manifest before comparing it with deployed images. The recorded 51-migration schema comparison and deployed `87fec723…` release are historical evidence. The current staging ledger, running digests, grants and ingress config remain unknown.
- A new disposable PostgreSQL 18 drill reproduced the critical restore hazard. A guest credential active at backup time was revoked on the synthetic source after the backup. The restored database accepted it until the known revocation was applied. A scoped forward retirement on the clone rejected the credential, a second run changed zero rows, and history survived. Another active Cart replayed its original receipt, an already-retired credential remained denied, and the projection consumer processed three pending events once. This validates the reconciliation mechanism with a known record. The completeness of real revocation history and Account Cart continuity on a current staging backup remain unverified.
- The existing staging status implementation reads ordered migration names, recorded release, running and Quadlet image references, and service states. The convenience CLI prints only a summary. The deployment executor requires the target ledger to match before apply. The backup tooling distinguishes checksummed/off-host-verified data from an independently verified restore, and a database-only checkpoint cannot qualify as coordinated recovery. No application or infrastructure configuration changes were needed for this review.

## Controlled rehearsal

1. On the approved staging host, use the existing read-only status and inventory actions as the rootless Maevelle user. If the tooling is absent, request operator-supplied evidence or separate installation authorization. Check the backup manifest, encrypted artifact hashes, PostgreSQL version, media, and recorded source image digests. A new coordinated capture stops Maevelle API and Worker, so authorize the outage separately and use the exact capture plan ID.
2. Restore database and media into the named quarantine target. Record baseline counts and scope, then apply the exact pending migration suffix once using the target API image's migration CLI and separate migration role. Check the ledger and Cart constraints. Stop on any failure and retain sanitized diagnostics. Verify synthetic or approved account access, existing lines, exact receipt replay, and pending/dead-letter state.
3. Before enabling any ingress, reconcile decisions between the backup recovery point and the cutover boundary, including guest revocations, account/session changes and deletions. Reapply 3214 when the snapshot predates it. That migration does not cover later revocations. Prove denial with a synthetic credential revoked after capture and confirm unrelated active authority is preserved if scoped reconciliation was selected. If evidence is incomplete and broad retirement is unapproved, keep the restored target offline.
4. Through the authorized Nginx → Caddy → API path, record actual socket peers and prove only the intended proxy can originate from each trusted peer. Exhaust one synthetic client's quota while another remains eligible, test forged and repeated forwarding headers, and verify backend ports are unreachable externally. Check secure cookies, private caching, foreign Origin rejection, account switching and Admin denial without the capability. Review API, proxy and trace sinks with synthetic success, denial and upstream-failure canaries. Confirm least-privilege roles and alerting, then restart the isolated Worker with a backlog and verify deduplication and drain.
5. Compare outcomes with agreed recovery objectives and keep the backup ID, exact digests and migration ledger in the release record. Promote only after separate deployment approval. Recover with a previous image/config only if compatible with the resulting schema and revocation rules. Otherwise rehearse forward repair or seek explicit authorization for coordinated restore. Preserve the failed attempt, receipt/outbox linkage and any reconciliation record.

Existing operator procedures are in the [staging deployment guide](../phase-05-operator-staging-deploy.md) and [backup runbook](../../staging-recovery-backup.md). No live host, persistent database, historical log, or production secret was accessed during this review.
