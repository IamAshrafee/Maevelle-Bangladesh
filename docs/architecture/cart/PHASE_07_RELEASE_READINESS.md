This review carries forward [Phase 04-C local closure](PHASE_04B_STOREFRONT_INTEGRATION_REPORT.md#phase-04-c-focused-closure) and the [Phase 06 analytics contract](../../domains/analytics/analytics-reporting-architecture.md#admin-cart-analytics-phase-06).

## Security and data integrity

- **PASS locally, High defect fixed.** Fastify logged raw Shopper Auth verification query tokens and password-reset path tokens. A synthetic canary reproduced both leaks. Shopper Auth now skips automatic raw URL logging, omits raw errors from its API diagnostics, sets private no-store before early rejection, and uses one reset-link quota per IP rather than one per token. Regression coverage checks the canary, early rejection and the durable counter. The edge and any historical logs still require operator review.
- **PASS for inspected controls and focused local paths.** Guest authority binds a credential hash to its exact cookie slot, tenant, currency and live lifecycle. A failed Shopper Auth lookup cannot supply guest authority. Account writes bind an active customer/account/user and the observed Cart context. Merge locks the destination before the source, retires the guest credential atomically, and permits only authenticated, exact account receipt replay after revocation. Wishlist Move checks source intent and commits removal with the Cart, receipt and outbox. Cart transaction retry and the established Shopper Auth lock-order correction were preserved.
- **PASS for inspected privacy boundaries.** Private Cart responses carry no-store, and writes require exact Storefront Origin, acceptable Fetch Metadata when supplied, and JSON. Recovery stores owner-scoped command intent in session storage and cross-tab signals separately. Guest and Shopper Auth bearer credentials use HTTP-only cookies. Admin reporting is tenant-scoped through active membership and `analytics.view`. Consented browser observations omit credentials and identifiers and remain separate from committed, internally linkable Cart facts. Confirm these properties at the real edge before launch.

## Release blockers in severity order

1. **Critical — persistent continuity and recovery.** Identify the deployed migration ledger and last compatible image digests. Obtain an authorized encrypted database backup and matching media snapshot, verify checksum and off-host recovery access, and restore into a quarantined target with no provider egress. Rehearse the exact populated upgrade and record lock time, affected rows, receipt/outbox counts, account continuity and revoked-credential denial. Set owner-approved recovery point/time objectives and verify them in the drill.
2. **High — ingress rate isolation and secret handling.** Cart and Shopper Auth derive quotas from Fastify's socket IP. The checked-in Caddy configuration proxies all API traffic to Fastify, which has no trusted-proxy setup. Public users can therefore share the proxy's quota and one client can starve others. Fix the client-address contract with the actual Nginx/Caddy topology, including an explicit trusted ingress boundary and edge replacement of untrusted forwarding headers. Prove that two independent clients have separate quotas, spoofed forwarding headers cannot evade limits, and direct API access is unavailable. Keep raw auth paths, query strings, cookies and coupon values out of proxy, API, trace and provider diagnostics. Have the operator assess historical logs and invalidate exposed capabilities if exposure is confirmed.
3. **High — deployed security and service controls.** With authorization, verify TLS chain, hostname and HTTP redirect, the intended public Host and scheme, Shopper Auth callbacks, and `/admin` routing. On success, denial and error responses, inspect host-only Secure/HttpOnly/SameSite cookies and private no-store behavior through the actual edge. Try a foreign Origin, invalid session, switched account, and an Admin lacking `analytics.view`. Inspect Maevelle-only listeners, network and volumes. Prove API and Worker roles can run their workflows while DDL and unrelated schemas are denied, and that migration uses a separate authorized role. Verify restricted secret files, provider egress, `/api/health/live` and `/api/health/ready`, restart policies, service logs and alerts for 429/503, lock waits, pending age and dead letters.
4. **High — privacy and commerce approval.** Approve retention, deletion, analytics activation and Cart presentation/eligibility rules below. Add a deletion or anonymization procedure that covers the live Cart, linked facts, receipts, source outbox, backups and post-restore handling.
5. **High — release workload and human acceptance.** On representative isolated data and through the approved edge, run a short mixed workload with account edits, merge and Wishlist contention, report reads and Worker backlog. Record p95 latency, database pool/lock pressure, 429/503, deadlocks and backlog drain against agreed limits. Run the manual device checks below. Defer additional indexes, aggregate tables and broader load tooling until these measurements justify them.

A synthetic custom-format dump restored into a separate database with fail-on-error, single-transaction `pg_restore`. - **BLOCKED for persistent execution.** Review 1000 and 3213 foundation, 3214 irreversible retirement, 3215 integrity, 3216 account ownership, and 3217–3218 analytics. Before the authorized maintenance window, record the exact target, baseline ledger, approved manifest and backup ID. Quiesce affected writers, check legacy rows against new constraints, then run the one-shot migration job. Stop on any failure and capture the ledger, SQLSTATE, lock and service diagnostics. Repair invalid data through a reviewed forward change and rehearse it on the clone before retrying.
- Start compatible API and Worker after schema verification, then Admin and Storefront. Confirm a live Bag, old credential denial, exact receipt replay and projection health before opening traffic. Transactional claims leave interrupted work pending. On restart verify pending age falls and facts stay unique. Investigate dead letters before any controlled replay. Never independently discard receipts or republish committed Cart intent.
- Image rollback requires a prior release verified compatible with the resulting schema and credential policy. If none exists, use forward repair or an explicitly authorized coordinated restore. A backup taken before credential retirement may only be exercised in quarantine until retirement and later revocations are reconciled. Record any post-backup writes lost or needing reconciliation before reopening.

## Focused verification and performance

Nineteen focused cases passed across the security, recovery and concurrency runs. The first filtered password-reset run omitted the existing signup fixture and failed at login. Rerunning with that prerequisite passed without changing the test. The guest-discovery lock regression, API typecheck and build, and whitespace check also passed.

The 2-, 20- and 100-line merge previews each used 20 SQL statements, with local medians of 18.62, 18.45 and 21.92 ms over five samples per size. The over-cap preview declined to project. Cart transactions have lock and statement timeouts, and the Worker claims bounded batches with SKIP LOCKED. The report is capped at 366 days and committed facts have a tenant/date index. Representative report plans, API authentication latency and Worker throughput remain open. Local timing does not establish production capacity.

## Owner decisions

| Decision | Recommended release default and implication |
| --- | --- |
| Cart retention and deletion | Keep current guest credential expiry and seven-day receipt replay. Approve a separate post-expiry deletion interval for guest records and an inactivity or account-deletion rule for Account Bags. Prefer a dry-run inventory and explicit deletion approval before scheduling cleanup. Expiry alone leaves historical rows. |
| Analytics and consent | Approve a short browser-observation window and a separately justified operational fact/source-outbox window. Keep external providers disabled. Require affirmative analytics consent for first-party observations and separate approval for any external destination. Shorter retention limits trend depth. |
| Email verification replay | Approve the existing provider-idempotent verification behavior or retain the strict single-use gate and implement it separately. Historical tests found no session issuance from repeat verification. Password reset has a separate single-use contract. |
| Quantity, stock and guest merge | Retain existing server ceilings, no stock reservation in the Bag, and explicit same-tenant/currency merge review. Preserve unavailable intent for review and block over-limit merges. Approve whether tighter per-product caps or eligibility should apply. |
| Promotions and delivery | Keep only explicitly configured stacking, treat Bag coupon eligibility as provisional, and avoid promising redemption or delivery before destination and authoritative eligibility are known. Approve stacking, redemption and location rules before rollout. |
| Tax and compare-at | Present evaluated merchandise values and substantiated compare-at pricing. Approve whether and where tax is included and what customers see before location is known. |
