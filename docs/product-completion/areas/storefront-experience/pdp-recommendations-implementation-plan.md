# Product recommendations — implementation plan

**Status:** Implemented locally across migration, API, Admin, Storefront, and consented discovery reporting. Focused migration, domain, type, lint, and production-build checks run; owner quality review and staging verification remain open.
**Prepared:** 2026-10-30.
**Feature authority:** [PDP recommendations feature plan](pdp-recommendations-feature-plan.md).
**Execution rule:** Deliver the complete PDP discovery capability: contextual ranking, merchandising, Storefront display, and discovery measurement. Check off a stage only with source and runtime evidence. Wishlist, Cart, and Checkout changes, including purchase attribution, are separate later work requested by the owner and must remain visibly open.

## 0. Repository facts that shape the build

- Public routes use `/storefront/v1` and `{ data }`; the PDP is `apps/storefront/app/products/[handle]/page.tsx`. Its current general-search cross-sells and the six hard-coded fallback cards must be removed.
- `catalog.products` and `catalog.product_variants` are organization-scoped UUID entities. Catalog has categories, Product Types, tags, occasions, collections, reference attributes, option values/colors, and coherent-variant filtering. `search.catalog_documents` is a rebuildable projection, not catalog or stock authority.
- Current public detail pricing calls `resolveVariantPrice` per variant. Cart add (`packages/database/src/cart.ts:addGuestCartLine`) requires an active published Product/Variant, positive available-to-sell quantity, and a current Pricing definition. It does **not** currently permit `CONTINUE` backorders. Recommendation eligibility must match the actual Cart add behavior: positive available-to-sell stock and current price. Do not advertise a backorder exception until Cart/Checkout implement one coherently.
- Cart and Checkout routes, database workflows, and tests already exist. Wishlist has a local-storage UI with sample entries and simulated move-to-bag behavior; it is not a complete authoritative wishlist. This recommendation task will not reimplement or change those areas.
- `CommerceEventDto` already defines `PRODUCT_LIST_VIEWED` and `PRODUCT_SELECTED`; browser ingestion is analytics-consent gated, failure isolated, and event-ID deduplicated in `analytics.storefront_events`. No recommendation events are emitted today. Existing Storefront analytics reports can host a placement-specific discovery view without a second analytics system.
- `components/commerce/product-card.tsx`, Price/Money, Media, and WishlistButton already exist. ProductCard currently shows a local heart toggle even without a persistence callback, so recommendation use must offer a genuine navigation-only variant or conditionally omit that control. Do not create a competing product card.
- Product edit is the `ProductCreator` route and has a section navigation strip; Product details and the Product list are separate. Admin API calls use shared helpers and Team & Access capabilities. Existing `catalog.manage` grants are broad; recommendation curation and global strategy need their own explicit grants.
- Latest registered migration at planning time is `3206_media_rendition_repair`. Register new, forward-only Kysely migrations after the current head. Preserve staging data; do not edit earlier migrations or reset staging as part of this feature.

## 1. Concrete domain model and migration work

Create a `recommendations` schema with a small normalized core, in one or more new migrations after the current head. Use the repository's UUID, `organization_id`, `version bigint`, `timestamptz`, composite tenant foreign key, check, and index conventions. Register each migration in `packages/database/src/migrations/index.ts`.

| Structure | Required fields and constraints | Access path |
| --- | --- | --- |
| `recommendations.placements` | `(organization_id, code)` key; enabled, strategy key/version, target count, minimum score, bounded candidate limit, fallback policy, version, actor/time. Seed `pdp_complementary` (3) and `pdp_similar` (4) for existing and newly provisioned organizations. | Organization + placement; versioned updates. |
| `recommendations.product_settings` | `(organization_id, source_product_id, placement_code)` key; mode `AUTOMATIC/HYBRID/MANUAL`, optional count/threshold overrides, enabled override, version, actor/time. Composite Product and placement references. Absence means inherit global settings. | Source Product + placement. |
| `recommendations.product_actions` | Directed source Product, target Product, placement, action `PIN/BOOST/EXCLUDE`, ordered pin position or bounded boost amount, active state, version, actor/time. Reject self-link, duplicate active action, and cross-organization Product references. | Source + placement + action + position; reverse target index for invalidation/coverage. |
| `recommendations.compatibility_rules` | Organization-scoped directed source/target classification (prefer Product Type or specific Category), active status, bounded strength, version, actor/time. Reject self-pair only where it has no business meaning; allow a deliberate same-type rule if useful. | Source classification + active state; unique active rule identity. |

Use `audit.audit_events` for configuration and relationship mutations, with before/after and actor membership. If downstream candidate invalidation needs an outbox event, write it in the same transaction as the configuration change. Do not create a separate product/price/stock snapshot table. Extend `analytics.storefront_events` only if discovery reporting queries demonstrably need indexed recommendation dimensions; its existing JSON payload can first carry validated placement/request/position data. No precomputed candidate table is part of the first implementation.

Add Team & Access capabilities `recommendations.view`, `recommendations.curate`, and `recommendations.manage`. Grant Owner in the migration, map the Product-level UI to view/curate, and reserve global strategy/compatibility changes for manage. Keep discovery analytics reporting behind `analytics.view`. Existing roles receive no silent new grants beyond Owner; operators can be granted explicitly. Add them to Admin navigation/permission descriptions where the existing capability catalog requires it.

## 2. Contracts and API surface

Add typed request/result DTOs and validation in `packages/contracts/src` using existing naming, decimal-string money, `PaginationDto`, and error conventions. Do not copy the illustrative `priceMinor` contract from the conversation. Define `RecommendationPlacementCodeDto`, `RecommendationCardDto`, `RecommendationSectionDto`, `ProductRecommendationsDto`, and Admin configuration/preview/coverage DTOs. The card reuses Storefront Product identity, title/handle, current `amount` and `currency`, Media asset IDs, and optional supported reason; no internal score or private explanation appears publicly. A response-level `recommendationRequestId` is a UUID for discovery measurement; section strategy/version and item position are stable and explicit. Do not add a purchase-attribution token or Cart contract in this task.

| Route | Behavior | Boundary |
| --- | --- | --- |
| `GET /storefront/v1/products/:handle/recommendations?organizationId=...&currency=...&placements=...` | One bounded response for both PDP placements. Validate source as public; allow only known placement IDs; return an empty section for no eligible candidates, 404 for unavailable source. | Public, organization resolved/validated against the configured Storefront as existing routes do. |
| `GET /admin/recommendations/placements` and `PATCH /admin/recommendations/placements/:code` | Read/update global placement settings with expected version and 409 conflict. | `recommendations.view` / `recommendations.manage`. |
| `GET/PATCH /admin/recommendations/products/:productId` | Read/replace only the supplied placement settings/actions, with expected version and atomic validation. Preserve unrelated placement settings. | `recommendations.view` / `recommendations.curate`. |
| `POST /admin/recommendations/preview` | Evaluate a saved or proposed configuration without committing; return ordered cards, score components/eligibility explanations, skipped pins, and rule/version context. Bound the input and work. | `recommendations.view` for saved; `recommendations.curate/manage` for proposed edits. |
| `GET /admin/recommendations/coverage` and `GET /admin/recommendations/product-picker` | Server-paginated, searchable worklists with counts, reasons, filters, and deterministic sort. | `recommendations.view`; catalog eligibility enforced. |
| `POST /admin/recommendations/bulk` | Bounded selection, dry-run preview, then versioned, idempotent apply with per-Product outcome and no overwrite of unrelated choices. | `recommendations.curate` or manage for global changes. |
| `GET/PATCH /admin/recommendations/compatibility-rules` | Paginated directed rule management and versioned mutation. | `recommendations.view` / `recommendations.manage`. |
| `GET /admin/recommendations/performance` | Placement/strategy discovery metrics with explicit denominators, period, and consent coverage; no revenue claim. | `analytics.view`. |

Place Fastify route registration in a focused `apps/api/src/routes/recommendations.ts`, with smaller Admin/public route modules if it grows; register it from `routes/auth.ts`. Use shared capability context and error envelope. For product and placement writes, use expected version in the same style as existing Catalog APIs; return 409 with reload/retry details. Treat an unknown placement, malformed UUID, excessive count/boost, self-link, or cross-org target as a validated error. Do not let public caller-supplied `organizationId` read another tenant's recommendations through the configured Maevelle Storefront endpoint.

## 3. Recommendation engine and authoritative projection

Implement focused database/domain files under `packages/database/src/recommendations/` (types/configuration, candidate query, eligibility/card projection, ranking, management, reporting). Export from a focused package entry point. Keep Fastify transport and Admin display logic out of these modules.

1. **Load source and configuration:** confirm the requested Product is active, published, and structurally coherent; load global placement and Product overrides once. Disabled sections return empty. Generate a request ID independent of a visitor identity.
2. **Collect bounded candidates:** include ordered manual targets, classification-compatible Products, category/Product-Type/collection/tag/occasion/attribute/color matches, and only explicitly permitted discovery candidates. Use tenant-scoped indexed queries and a fixed candidate cap. Do not scan all Products per request or derive meaning from product title text. Evaluate both placements together where a shared read is cheaper.
3. **Hard-filter in one bulk read:** recheck Product/Variant/public Media and use a batched current-price query with the same active/effective/currency ordering as `resolveVariantPrice`; use active inventory items and positive `sellable_quantity - reserved_quantity`, matching Cart's current rule. Require a priced, stocked **same variant**, so a cheap unavailable SKU cannot set the display price for a different available SKU. Set card price to the minimum current eligible variant price, with deterministic variant tie-breaking. Media selection follows the public Search/Product card placement rules and `card` rendition. Keep Cart/Checkout revalidation unchanged.
4. **Score and diversify:** pins first after eligibility; exclusions before pins/boosts; strategy-specific weights and minimum score; bounded boosts; deterministic ties by score, pin position, publication recency if needed, then Product ID. Similarity uses structured commonality and a configurable price band. Complementarity requires directed curation or an explicit compatibility rule plus adequate aesthetic relevance. Deduplicate across placements, preserving an eligible pinned item in its designated placement if possible; define conflict output in Admin preview.
5. **Return and explain:** public projection contains only safe card data, placement/version, request ID, and item position. Admin preview includes score components and reasons for omitted manual items. Zero suitable candidates returns zero cards, never generic fill.

Start with a versioned rule strategy (for example `contextual_v1`) and configuration bounds tested against representative Maevelle catalog examples. Store weights as validated, versioned configuration rather than free-form unbounded JSON. Use one evaluation path for public and Admin preview; preview may add explanations but may not use weaker eligibility. Strategy interfaces should accept additional candidate/ranker sources later without changing placement IDs or public cards.

Keep placement and strategy identifiers stable so a later Cart/Checkout integration can add validated item-level attribution without changing the ranking engine or public placement IDs. Do not predesign a token, signing secret, Cart mutation, or Order schema in this PDP task.

## 4. Admin implementation

- Add a reusable `ProductRecommendations` section to the existing Product editor and detail handoff, and a navigation entry in `creator/section-nav-strip.tsx`. A new Product gains an ID after creation; show a clear “save Product first” state and open the same section in edit mode after creation. Use shared Admin page, form, table, status, dialog/sheet, and error primitives.
- Build a paginated searchable Product picker with thumbnail, state, current price/stock cue, and exclusion of the source Product. Pin/reorder via move-up/down controls usable by touch and keyboard; optional drag UI must call the same reorder command. Show boost/exclude actions, saved vs pending state, validation, conflict recovery, and a live preview whose explanations distinguish “configured” from “displayed.”
- Add `/admin/recommendations` for placement defaults, compatibility rules, coverage/quality worklist, bulk actions, performance, and operational diagnostics. Keep global strategy forms bounded and grouped; expose advanced weights only with descriptions and preview. Search/filter/sort and pagination belong in URL state where lists can grow. Restrict controls and server endpoints by capability.
- Add coverage and invalid-pin cues to the Product list/detail without making recommendations a publication prerequisite. Use Product/Media/Pricing/Inventory links for data correction, preserving their ownership. Reuse one form model for per-Product changes rather than duplicating create/edit logic.

## 5. PDP and measurement implementation

- Add `lib/api/server/recommendations.ts` for the public typed fetch. Render the recommendation region separately from primary Product data, preferably as a streamed Server Component/Suspense region after checking this repository's installed Next.js guidance. A rejected/slow fetch yields no section and a diagnostic; it must not reject the PDP response. Reserve card geometry only while content is expected; avoid decorative loading that increases shifts.
- Replace `pdp-cross-sells.tsx` and its `CrossSellProduct` ad-hoc type with a placement-driven component. Remove the general `searchPublicCatalog` call from the PDP route and every hard-coded example image, fake badge, zero-price fallback, and “Curated” label without evidence. Reuse ProductCard/Price/Media; extend ProductCard's shared API so a recommendation card can omit the heart when Wishlist is not wired. Show no pretend quick-add/bag control. Keep viewport/click tracking as a small client island and do not move the whole PDP further into client state.
- Extend shared commerce event payloads with optional `listId`/placement, request ID, target Product, and item position where the existing event shape lacks them. The card projection must include the selected eligible presentation SKU required by the existing `CommerceItemDto`; never invent a SKU ID. `PRODUCT_LIST_VIEWED` is emitted when a section's cards are actually visible (IntersectionObserver, one logical event per page/placement/request); `PRODUCT_SELECTED` is emitted on interaction. Use the existing consent-gated `publishCommerceEvent` path; do not call GA4 directly. The link to the recommended PDP remains functional without analytics consent or JavaScript measurement.
- Build discovery reporting from observed impressions, clicks, CTR, Product-page continuation where reliable, coverage, and strategy version. Expose denominators, date window, missing-consent coverage, and empty-data states. Do not infer attributed carts, orders, revenue, AOV lift, or causal impact from clicks.

| E — Discovery measurement | Event contracts, visible impressions/clicks, placement reporting. | Consent/dedup tests, honest denominators, and analytics outage does not block shopping. |

Checkpoints are manageable implementation increments, not alternate product boundaries. Do not call the PDP discovery capability complete after B or D while Admin and discovery measurement are missing. Do not describe Cart/Order attribution as complete at F. Keep `docs/product-completion/` progress concise; update this plan if source evidence changes a decision.

## 7. Focused verification matrix

- **Domain/database:** same-org and cross-org links; self-link; pin/exclude precedence; stale version; audit; mode/override inheritance; missing attributes; compatibility direction; deterministic ranking/diversity; no duplicate cross-placement Product; missing stock/price/media; stale search projection; relevant two-item catalog; zero-item response.
- **API/security:** public source visibility and tenant scoping; invalid placements/counts; admin capability matrix; pagination; conflict errors; preview parity; bulk dry-run/apply; request bounds and abuse controls.
- **Discovery analytics:** consent denied/unknown, impression and click deduplication, placement/request/position integrity, honest CTR/coverage, analytics endpoint failure, and no purchase/revenue claim.
- **Frontend:** 320–390 px mobile, tablet/iPad portrait and landscape, intermediate and desktop; no horizontal overflow or layout shift; touch targets, keyboard reorder/scroll, focus, accessible headings/labels, reduced motion, long Bangla/English names, empty/loading/error states, fast PDP navigation, ProductCard image and price accuracy, and no inert wishlist/bag control on recommendation cards.
- **Operational:** migration status before affected services, API/Worker/Admin/Storefront compatibility order, recommendation query latency and result coverage, publication/price/stock freshness, service logs and health, and a focused browser smoke after a staging deployment. Record release SHA/digests and rollback compatibility in the deployment log when deployed.

Run the narrow tests/typecheck/lint for each checkpoint. Run a Storefront production build when route/rendering changes, and a broader cross-domain verification at integrated closure or when a high-risk change warrants it. The implementation plan does not authorize a staging reset or a production deployment.

## 8. Resolved choices and implementation-time checks

**Resolved for this build:** two PDP placements; contextual rule engine with directed compatibility; sellable-only per current Cart semantics; no random filler or fake curation; tenant-scoped Admin management; current price/stock at response; consented discovery measurement; existing shared ProductCard; no Cart/Checkout/Wishlist mutations; no new service or ML dependency; no precomputed candidate snapshot until measured need.

**Check in code before the corresponding edit:** exact current migration head; whether the Admin Product creator can host a post-save recommendation section cleanly or should link to a focused detail tab; installed Next.js Server Component streaming/caching guidance; how ProductCard can omit an unwired Wishlist control through a reusable API; representative seeded attribute quality and compatibility examples. These checks refine implementation details without reopening the feature's core behavior.

**Explicit later integration:** When the owner takes up Cart/Checkout, design exact item-level recommendation context, consent, cart-add idempotency, order-line snapshots, COD/return/refund treatment, and financial reporting against their then-current code. The existing modules are real; this task simply leaves them untouched. The later integration has its own acceptance evidence and is never inferred from PDP click metrics.
